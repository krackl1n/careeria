# Notification Service: проектирование

**Статус: проект, не реализованный API и не миграции.** [Юзкейсы](use-cases.md), [DBML](../../data-model/notification/schema.dbml) и [проект SQL-ограничений](../../data-model/notification/constraints.sql) развивают [C4 L3](../../architecture/c4/plantuml/system-context%28L1%29/full-system%28L2%29/notification-service%28L3%29/index.md). Схема не применялась к PostgreSQL; контракт внешних систем и ряд продуктовых правил ещё не утверждены.

Обычные изменения агрегата выполняются с ожидаемой версией по [общим правилам конкурентного доступа](../../data-model/concurrency.md). Исключения для общих инвариантов и очередей описаны ниже.

## Назначение и соответствие C4 L3

Notification Service принимает запросы и бизнес-события, готовит уведомления, хранит задачи и inbox, отправляет сообщения через внешние каналы и передаёт in-app push. Он не является источником факта найма или членства компании и не принимает решений за эти сервисы.

| Компонент L3 | Ответственность |
|---|---|
| **Notification Service** | Единственный показанный application service: Schedule, Cancel, FetchPending, Execute, чтение inbox и координация stream. |
| gRPC Server / Stream Server | Синхронные запросы и пользовательский поток; доверенная identity обязательна. |
| Events Consumer | Чтение Kafka, декодирование через Schema Registry и передача в прикладной сценарий. |
| Worker Pool | Ограниченное конкурентное исполнение задач через application service. |
| Template Repo / Job Repo / In-App Repo | Локальное хранение и выборки шаблонов, задач и inbox. |
| Template Engine | Рендеринг неизменяемой редакции шаблона; безопасное экранирование для канала. |
| Notification Provider Adapter | Изоляция провайдеров email/push/SMS; формат ошибок и поддержка идемпотентности зависят от провайдера. |

Все компоненты находятся в одном сервисе. L3 не показывает OpenFGA, outbox, provider callback или управление шаблонами через отдельный API. Локальная авторизация и входящие service credentials всё равно необходимы; добавление новых зависимостей и компонентов требует изменения C4. Текст L3 не определяет распределённую доставку локальных Go Channels между экземплярами Stream Server и workers — это открытая архитектурная задача, а не гарантия текущей диаграммы.

## Модель и границы

| Корень | Ответственность |
|---|---|
| NotificationTemplate | Идентичность шаблона и его жизненный цикл. |
| TemplateRevision | Неизменяемая после публикации редакция конкретного канала и локали; новые изменения — новая редакция. |
| DeliveryJob | Одна доставка одному получателю одним каналом по конкретной редакции, расписание, состояние и lease. |
| InAppNotification | Один сохранённый снимок для получателя; отдельное прочтение или удаление в текущую L3 не входит. |

Одно событие может породить несколько независимых jobs по получателям и каналам. Общая сущность кампании/логической нотификации сейчас не вводится: отмена одной job не отменяет остальные. Если понадобится общая отмена или агрегированный статус, её контракт и модель нужно спроектировать отдельно. Канал и локаль принадлежат неизменяемой редакции; job не дублирует их. В inbox намеренно хранится снимок показанного текста, независимый от последующих изменений шаблона, с получателем: составной FK гарантирует его совпадение с получателем job. Уникальность `delivery_job_id` предотвращает два inbox item для одной in-app job; что job действительно IN_APP, проверяет транзакционный сценарий, а не этот FK.

Ревизии и API управления шаблонами — проектное расширение: L3 показывает загрузку шаблонов, но не операции их публикации. Кто создаёт/публикует редакции, как выбирается локаль и что делать при отсутствии шаблона — требуется определить. Предполагается зафиксировать revision ID и входной payload при Schedule, чтобы последующее изменение шаблона не изменило уведомление. Перед первой внешней отправкой рендерится и устойчиво фиксируется снимок текста; повторы используют его, а не новые данные/шаблон. Путь адресата и правила изменения адреса, токена устройства или телефона между попытками ещё не утверждены; схема не содержит предполагаемого источника адресов и не гарантирует доставку без него.

## Состояния и конкурентная обработка {#delivery}

Предлагаемые состояния DeliveryJob: PENDING → PROCESSING → SUCCEEDED, RETRY или FAILED; PENDING / RETRY → CANCELLED. После наступления `scheduled_at` или `next_attempt_at` worker может захватить job. При отмене PROCESSING возвращается конфликт: отправка могла уже начаться, и отзыв письма не гарантируется. Истёкший lease восстанавливается в повторяемое состояние с учётом неопределённого результата предыдущей попытки. Правила повторов, срок жизни, backoff, rate limits и обработка постоянных ошибок надо согласовать.

FetchPending выбирает ограниченную порцию через `FOR UPDATE SKIP LOCKED`, присваивает уникальный lease token и срок и коммитит короткую транзакцию. Сам `SKIP LOCKED` не удерживает право на задачу после commit. До вызова провайдера исполнитель повторно проверяет PROCESSING и token и фиксирует номер и начало attempt. Сеть вызывается вне SQL-транзакции. Завершение применяет результат только при актуальном token и версии; устаревший worker не может перезаписать более новое состояние. Lease и token **не предотвращают** второй внешний вызов старым worker после истечения lease: попытки могут пересечься, если провайдер не поддерживает идемпотентность.

Для внешнего канала SUCCEEDED означает принятие запроса провайдером, не доставку или прочтение. Провайдеру передаётся стабильный ключ job, если его API это поддерживает, и фиксируется допустимый идентификатор ответа. При потере ответа неизвестно, принят ли запрос; повтор может создать дубль. Если провайдер не поддерживает ключ или запрос статуса, политика повтора/ручной разбор неопределённого результата должна быть согласована. Строгую exactly-once доставку обещать нельзя. Provider callbacks и подтверждения доставки не показаны на текущей L3.

Для IN_APP создание inbox item и перевод job в SUCCEEDED выполняются в одной транзакции с уникальностью `delivery_job_id`; затем stream передаёт сигнал после commit. Сбой push не удаляет сохранённое уведомление. L3 не обещает read receipts и пользовательское удаление; `read_at` из прежнего DBML удалён до появления соответствующего сценария.

## События, дедупликация и stream

Events Consumer проверяет envelope и схему, затем по утверждённому правилу выбирает получателей, каналы и редакции. В одной транзакции создаётся **полный набор** jobs и `(consumer, source_event_id)` с исходом; только после commit подтверждается offset. Повтор не создаёт новый набор. Для больших списков получателей потребуется отдельная устойчивая модель fan-out и её уникальные ключи; один маркер до завершения частичной обработки не годится. Неизвестные события, невалидные сообщения, доступность Schema Registry и политика quarantine/DLQ ещё требуют контракта.

Schedule по gRPC принимает доверенного сервисного инициатора, проверяет право создавать уведомления данному получателю, фиксирует create_request_id и хеш непосредственно в DeliveryJob. Это не заменяет журнал обработки входящего Kafka-события. Повтор с тем же хешем позволяет найти созданную задачу после проверки прав, другой хеш — конфликт; после удаления записи распознать повтор нельзя. Обычный пользователь не выбирает произвольную identity для чтения inbox: запрос ограничивается доверенной identity; административный доступ требует отдельного права.

Stream Server направляет уведомления только авторизованному получателю; медленный клиент и разрыв не должны блокировать Worker Pool. Клиент после переподключения читает inbox и устраняет дубли по ID. Простая пагинация `(created_at, id)` удобна для истории, но **не доказывает отсутствие пропусков** при конкурентных транзакциях и времени commit; точный протокол subscribe/replay с устойчивым курсором и межрепличной доставкой должен быть спроектирован до обещания полного восстановления. Текущая L3 использует локальные Go Channels; при нескольких репликах требуется отдельное решение и, вероятно, обновление C4.

## Хранение и открытые решения

DBML показывает основные PK/FK, индивидуальные редакции, job, журнал попыток и inbox. Нормализованные бизнес-ссылки не доказывают автоматически строгую 3НФ всей системы: payload рендеринга и сохранённый текст — технические/исторические снимки; дублирование текста job и inbox намеренное и требует срока хранения. CHECK/FK не обеспечивают неизменяемость редакций, допустимость канала inbox, корректность lease fencing или атомарность сценариев. `constraints.sql` — предварительная часть миграции, а не исчерпывающий контракт.

До реализации нужно согласовать авторизацию Schedule/Cancel и stream, источники и защиту адресов, версионирование и управление шаблонами, форматы и срок хранения персональных данных, fan-out, retry и неопределённый результат провайдера, stream/replay между репликами и лимиты буферов, а также API провайдеров. Нужны PostgreSQL-тесты атомарности дедупликации, двойного claim, истечения lease и старого worker, гонки Cancel/Execute и создания inbox, а также интеграционные тесты провайдеров и нескольких stream-реплик.
