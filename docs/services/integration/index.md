# Integration Service: проектирование

**Статус: проект, не реализация и не миграции.** [Юзкейсы](use-cases.md), [DBML](../../data-model/integration/schema.dbml) и [проект SQL-ограничений](../../data-model/integration/constraints.sql) развивают [C4 L3](../../architecture/c4/plantuml/system-context%28L1%29/full-system%28L2%29/integration-service%28L3%29/index.md). Контракты внешних систем и применение схемы в PostgreSQL ещё требуют проверки.

Обычные изменения агрегата выполняются с ожидаемой версией по [общим правилам конкурентного доступа](../../data-model/concurrency.md). Исключения для общих инвариантов и очередей описаны ниже.

## Граница и компоненты C4 L3

Integration Service принимает подписанные webhook внешней HR-системы, нормализует их и планирует доставку внутренних событий во внешние системы. Он не изменяет отклики, вакансии или компании напрямую: факт приёма означает только фиксацию в Integration DB; бизнес-сервис сам обрабатывает и проверяет событие.

| Компонент L3 | Ответственность |
|---|---|
| **Integration Management Service** | Подключения, подписки, ключи, просмотр журналов, отмена и ручной повтор. Управление требует доверенной identity и разрешения компании. |
| **Inbound Webhook Service** | Проверка подписи и свежести, нормализация, дедупликация и атомарный приём. |
| **Outbound Webhook Service** | Фильтрация внутренних событий, формирование deliveries, захват и выполнение попыток. |
| Webhook HTTP Handler / gRPC Server | Раздельные входы для raw HTTP и управления; webhook не использует пользовательскую сессию. |
| Events Consumer / Webhook Delivery Worker | Чтение Kafka с фиксацией offset после commit и выполнение отложенных jobs. |
| Inbound / Outbound Webhook Adapter | Версионированный provider mapping, сериализация и проверка/создание подписи. |
| Authorization Client / Integration Repo / Transactional Outbox | Проверка прав, локальное хранение, атомарная запись нормализованного входящего события. |
| Webhook HTTP Client | Контролируемый HTTPS POST к внешнему назначению. |

Компоненты — части одного развёртывания. Company и другие сервисы владеют своими данными; внешние идентификаторы не являются межбазовыми FK. Kafka/CDC доставляют события, но Integration не гарантирует их бизнес-применение в Hiring.

## Границы агрегатов и хранение

| Корень | Ответственность |
|---|---|
| IntegrationConnection | Принадлежность компании, provider/tenant, входной route, список допустимых типов и жизненный цикл. |
| WebhookSubscription | Одно внешнее назначение, жизненный цикл и выбор текущей редакции. |
| SubscriptionRevision | Неизменяемый снимок endpoint, версии контракта и ограниченного набора типов событий. |
| SigningKey | Отдельный ключ входящего подключения или исходящей подписки и его жизненный цикл. Координация ротации нескольких ключей — локальный протокол. |
| InboundReceipt | Один принятый provider message ID с digest, результатом и версией преобразования. |
| WebhookDelivery | Одна доставка события в подписку, фиксированные редакция и payload, состояние и lease. Попытки — журнал, который не загружается целиком. |

Входящие и исходящие ключи — разные таблицы: это исключает неоднозначный nullable владелец. Составные FK связывают текущую редакцию и доставку с правильной подпиской и запрещают использовать для попытки ключ другой подписки. Циклическая связь подписки и первой редакции создаётся через временный NULL внутри транзакции. Списки разрешённых событий — отдельные строки; JSON outbox и байты подписываемого payload — технические снимки, не нормализованный каталог. Историческая редакция и payload должны оставаться неизменными; это транзакционное правило, не обеспеченное текущим FK. Строгая 3НФ и физические индексы требуют проверки после утверждения бизнес-ключей и контрактов.

Состояние подключения: ACTIVE / PAUSED / REVOKED; REVOKED терминален. Подписка: PENDING_VERIFICATION / ACTIVE / PAUSED / DELETED. При изменении endpoint создаётся новая редакция и требуется повторная проверка; старая доставка не меняет назначение тихо. Правило атомарного переключения current revision и сохранения evidence handshake, его срок, nonce и audit ещё не спроектированы: DBML не доказывает верификацию адреса. Выполнение старых deliveries после изменения/отзыва endpoint должно быть согласовано с безопасностью и клиентами; до решения worker не должен молча перенаправлять их.

## Входящий webhook

1. API Gateway передаёт неизменённые raw bytes и signing headers; отдельный HTTP handler ограничивает размер/время чтения и не выполняет JSON-трансформацию до проверки подписи.
2. Route ID определяет подключение и компанию из собственной БД, не из недоверенного payload. Для ACTIVE-подключения проверяются выбранный протокол и допустимые ключи, timestamp, подпись по сырым байтам и правила конкретного provider mapping. Сравнение подписи выполняется в constant time. Формат Standard Webhooks из L3 и пятиминутное окно — предложения, а не универсальная политика для всех провайдеров.
3. После проверки принимается решение ACCEPTED или явно допустимое IGNORED. Уникальность `(connection_id, provider_message_id)` и digest исходного тела различают безопасный повтор и конфликт с другим содержимым. ACCEPTED и нормализованное событие в outbox фиксируются в одной транзакции; успешный ответ возвращается после commit. IGNORED не обязан иметь event ID. Неверная подпись, просроченный запрос и конфликт не маскируются успехом.
4. Доменный потребитель независимо проверяет идентификаторы, полномочия источника, актуальность и идемпотентность. Отсутствие cross-service транзакции означает, что ACCEPTED не равно применению изменения.

Одновременное обновление/отзыв ключа или PAUSE и входящий запрос требуют согласованной проверки состояния подключения и версии ключа непосредственно перед commit. Внешняя криптография не должна удерживать долгую блокировку; после вычисления нужно повторно проверить применимость использованных версии/состояния в локальной транзакции. Точная политика повторов и retention дедупликации должны быть согласованы с отправителем.

## Исходящая доставка и гонки {#delivery}

Events Consumer проверяет envelope и schema, выбирает только подписки компании-владельца события, соответствующие разрешённому типу. В одной транзакции фиксируются полный набор deliveries и `(consumer, source_event_id)`; offset подтверждается после commit. Уникальность `(subscription_id, source_event_id)` защищает от дублей планирования. Для больших fan-out нужна отдельная устойчивая модель, а не преждевременное подтверждение обработанного события.

Создание delivery закрепляет revision ID и точные байты payload/digest. Компания выводится через подписку и её connection, а не принимается из внешнего тела; историческая принадлежность подключения компании должна быть неизменяемой. Составной FK защищает принадлежность редакции. При изменении подписки и планировании события требуется согласованный локальный снимок состояния и блокировка/проверка версии, чтобы не назначить delivery по отозванной или непроверенной редакции. Поведение PAUSED и уже захваченных попыток должно быть определено в контракте.

Worker забирает due deliveries в короткой транзакции через `SKIP LOCKED`, присваивает lease token и срок, создаёт attempt с порядковым номером и выбранным ключом. Перед сетевым вызовом проверяются актуальные состояние, срок, действие подключения/подписки и возможность использования ключа. HTTP выполняется вне SQL-блокировок. Результат применяется условно по token и версии; старый worker не может изменить новое состояние. Истёкшая попытка фиксируется как UNKNOWN: получатель мог обработать webhook, хотя ответ потерялся. Повтор использует прежние delivery ID и байты; принимающая сторона должна дедуплицировать ID. Exactly-once доставка не гарантируется, и lease не предотвращает дублирующий внешний вызов после истечения срока.

CANCELLED запрещает новые попытки, но не может отозвать уже начатый HTTP POST. Redrive FAILED по тому же delivery ID требует аудита и явной политики дедлайна/лимитов; изменение payload или адреса должно быть отдельной новой операцией с новым ID и понятными последствиями для дедупликации. Ротация ключа не должна незаметно нарушать неизменность payload; допустимость подписи очередных попыток новым ключом и правила экстренного revoke нужно согласовать с получателем.

## Защита и открытые решения

Секреты сохраняются зашифрованными; encryption key ID ссылается на ключ вне БД. Способ выдачи первоначального секрета, безопасная одноразовая передача, KMS и ротация требуют решения. Секреты, подписи и полные ответы провайдера не включаются в обычные GET, payload, логи и идемпотентные ответы.

Исходящий HTTP client разрешает только утверждённые HTTPS destinations: необходимо проверять DNS и фактический IP при каждом соединении, блокировать loopback/private/link-local/metadata и иные недопустимые диапазоны IPv4/IPv6, не следовать redirects и не допускать DNS rebinding/прокси обход. Детали разрешения DNS, egress policy, проверка TLS имени и конфигурация proxy должны быть реализованы и проверены в интеграционных тестах, а не считаться гарантированными описанием. Размер ответа, timeout, retries, размер тела, частота и журналирование ограничиваются согласованной политикой.

DBML и SQL — проект основных ключей, FK и CHECK. Они не обеспечивают неизменяемость редакции/bytes, доказательство handshake, полную FSM, tenant isolation или корректность ротации. До миграций согласовать правила уникальности подключения/tenant и выбор активного ключа, политику проверки endpoint, ручной redrive, входные/выходные версии схем и retention персональных данных, атрибуты аудита, частичные индексы, outbox и криптографическую инфраструктуру. Требуются PostgreSQL-тесты конкуренции при приёме дубликата и изменении подписки, двойного claim, истечения lease/старого worker, а также интеграционные проверки SSRF, DNS rebinding, replay и потери ответов.
