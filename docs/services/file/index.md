# File Service: проектирование

**Статус: проект, не действующий API и не миграции.** [Юзкейсы](use-cases.md), [DBML](../../data-model/file/schema.dbml) и [проект SQL-ограничений](../../data-model/file/constraints.sql) описывают предлагаемую модель. Для File Service пока нет отдельной C4 L3: [общая модель L2](../../architecture/c4/plantuml/model/infrastructure-elements.puml) задаёт Go/gRPC, MinIO, multipart upload, ограниченные URL, проверки MIME/размера, antivirus hook и жизненный цикл. Внутренние компоненты ниже — предложение для будущей L3, а не её текущий состав.

Обычные изменения агрегата выполняются с ожидаемой версией по [общим правилам конкурентного доступа](../../data-model/concurrency.md). Исключения для общих инвариантов и очередей описаны ниже.

## Ответственность и границы

File Service владеет техническими метаданными файла, состоянием загрузки, проверками безопасности, привязками к ресурсам и безопасной очисткой. Байты находятся в приватном S3-совместимом Object Storage. Candidate владеет резюме, Communication — сообщением, Assessment — тестом, Hiring — откликом; они хранят внешние `file_id` и свои бизнес-данные. Один файл может удерживаться несколькими независимыми привязками, например версией резюме и откликом. File Service не решает самостоятельно, вправе ли рекрутер видеть конкретный отклик или сообщение.

Идентификаторы владельца и ресурса — внешние UUID без межсервисных FK. `owner_identity_id` не является корпоративной ролью или доказательством права на любой документ. Сервис-владелец ресурса определяется по доверенной service identity, а не произвольной строке клиента. Допустимые service/purpose/resource-type и делегирование доступа нужно зафиксировать в межсервисном контракте и политике авторизации.

## Предлагаемые компоненты для L3

| Компонент | Назначение |
|---|---|
| File Upload Service | Begin, выдача ограниченных прав загрузки, Complete, Cancel и восстановление состояния операции. |
| File Validation Service | Координация проверки точной версии объекта, обнаружение MIME/размера/checksum и antivirus hook. |
| File Binding Service | Создание и освобождение привязок, проверка прав сервиса и ресурса, выдача разрешённого доступа на скачивание. |
| File Cleanup Worker | Устойчивая очистка объектов/мultipart upload, lease, повторы и reconciliation. |
| gRPC Server, Authorization Client | Доверенный контекст, формат запросов и проверки полномочий пользователя и сервиса. Конкретная архитектура авторизации ещё не выбрана. |
| File Repo, Upload Repo, Binding Repo, Outbox | Локальные порты хранения и, если нужны, атомарная запись событий. Названия репозиториев и потребность в outbox — проектные, не утверждённый контракт. |
| Object Storage Client, Scanner Adapter | Изолированные операции с S3-совместимым хранилищем и сканером; конкретный сканер/развёртывание ещё не выбраны. |

Это роли одного развёртывания, не отдельные микросервисы. Доставка байтов не проходит через другие доменные сервисы; клиент загружает объект непосредственно по ограниченному праву. Реализацию проверки и режим хранения необходимо сначала подтвердить для выбранной версии MinIO/S3 и конфигурации, затем отразить на L3.

## Агрегаты и состояния

| Корень | Граница и инвариант |
|---|---|
| File | Технический жизненный цикл одного файла, владелец, назначение и проверенные метаданные. READY относится к конкретной неизменяемой версии байтов. |
| UploadSession | Одна попытка загрузки, идентификатор клиента, устойчивый begin operation ID и сроки предоставленных прав. |
| FileBinding | Одна стабильная связь файла с внешним ресурсом сервиса; повтор Bind не создаёт дубли. |

File: UPLOADING → CHECKING → READY или REJECTED; при отмене, истечении, отказе или освобождении последней связи возможен управляемый переход в DELETING → DELETED. CHECKING/READY относятся к неизменяемой версии объекта, а не к произвольному текущему содержимому по ключу. DELETING не принимает новые привязки или выдачу URL; DELETED терминален. Точная политика сроков ожидания, отмены после READY, восстановления ошибочной проверки и удержания файлов пока не утверждена. Отказ сканирования не равен технической недоступности сканера: ERROR остаётся для повтора или операционного разбора, не переводит файл в READY.

UploadSession: INITIALIZING → UPLOADING → COMPLETING → COMPLETED; разрешены CANCELLED/EXPIRED до завершения. Физическое удаление multipart upload и объекта может продолжаться после отмены. FileBinding: PENDING → ACTIVE → RELEASED либо PENDING → RELEASED; возвращение RELEASED к ACTIVE запрещено. Уникальный ключ `(file_id, owner_service, resource_type, resource_id)` означает: для повторного использования того же ресурса и файла нужна новая бизнес-модель, а не скрытая реактивация освобождённой связи. На уровне продукта нужно подтвердить, допустим ли такой запрет.

Одна привязка на конкретный ресурс не доказывает существование этого ресурса в другом сервисе. Идентификаторы Bind и Release хранятся непосредственно в FileBinding; повтор проверяет владельца, file ID и параметры связи. Для Begin ID и хеш запроса находятся в UploadSession. После удаления соответствующей записи нельзя обещать распознавание повтора; сроки хранения и порядок безопасных повторов требуют контракта.

## Загрузка и проверка {#upload}

1. Доверенный доменный сервис вызывает Begin с владельцем, purpose, характеристиками файла, target resource и устойчивым operation ID. Локально создаются File, UploadSession в INITIALIZING и PENDING-binding, фиксируется hash запроса. Повтор позволяет найти ту же операцию даже после потери ответа. Другие привязки к ещё неготовому файлу допустимы только по явно согласованной политике; исходная PENDING-привязка удерживает загрузку до завершения/отмены.
2. Создание multipart upload в S3 выполняется вне SQL-транзакции. Возвращённый storage ID привязывается к той же сессии. В случае потери ответа необходима согласованная стратегия восстановления по стабильному storage key или уборки неизвестного multipart upload: один локальный operation ID сам по себе не делает сторонний вызов идемпотентным. Клиент получает короткоживущее право загрузки только для выделенного объекта/частей. Срок каждой выданной ссылки записывается до выдачи; повтор не хранит старый URL, а получает новый после авторизации и проверки состояния.
3. Complete фиксирует намерение завершить операцию, затем вне SQL-транзакции завершает multipart и фиксирует **неизменяемый адрес байтов** для проверки. Например, при включённом versioning это object version ID, который нельзя подменить последующей загрузкой; альтернативно подходит контролируемое копирование в защищённый неизменяемый объект. Какой именно механизм гарантирован выбранной конфигурацией MinIO/S3 — предварительное решение для внедрения. Сканирование и скачивание обязаны адресовать именно проверенную версию; проверка только текущего объекта по ключу уязвима к замене между scan и download.
4. Validation проверяет реальный размер, MIME по содержимому, контрольную сумму и требуемые security checks конкретной версии. Значения из имени, заголовков и декларации клиента недоверенны. После положительного результата локальная транзакция повторно проверяет состояние File, неизменность адреса объекта и разрешённую привязку, фиксирует метаданные и READY; исходная привязка становится ACTIVE. Повтор Complete/reconciliation восстанавливает тот же результат. После отмены или DELETING поздний ответ не возвращает файл в READY.

Ограничения типа/размера зависят от purpose. Например, предполагаемые PDF/DOCX и 10 MiB для резюме ранее были лишь примером, не общей политикой всех файлов. Безуспешная проверка и безопасный код отказа не должны раскрывать внутренности сканера. ZIP-бомбы, архивы, лимиты времени и недоступность антивируса требуют отдельной политики. Состояние сканера и полученный результат привязаны к storage version ID; SQL-схема сама не гарантирует корректность вызова сканера.

## Доступ, привязки и очистка {#binding-cleanup}

Bind требует доверенного сервиса, подходящего purpose, права на ресурс и авторизованного владельца/делегирования. READY допускает отдельные bindings, включая привязку Hiring к версии файла, уже используемой Candidate; такая связь создаётся по согласованному протоколу Hiring/Candidate и не выводится из знания file ID. Перед выдачей download URL доменный сервис проверяет право на конкретный ресурс; File Service проверяет вызывающую сервисную identity, состояние файла и ACTIVE binding. Получение URL не является доказательством права на другие привязки или будущие ресурсы.

Bind, Release и решение начать очистку используют версию File как общий guard: каждый из этих путей выполняет CAS версии File и в той же транзакции заново проверяет bindings; изменения самих FileBinding также используют их версии. При конфликте вся транзакция откатывается, авторизация и правила проверяются заново. Если общий guard неприменим, допустимы короткие блокировки File и bindings в стабильном порядке. Очистка может перейти в DELETING только если нет ACTIVE **и PENDING** привязок и не действует установленная защита ожидаемой операции. В той же транзакции создаётся устойчивый cleanup job; последующий Bind на DELETING запрещён. Release одной связи не затрагивает другие связи. При повторном освобождении возвращается согласованный результат; поздний Bind/Complete не восстанавливает DELETING.

Cleanup worker захватывает job с lease и fencing token, проводит идемпотентные операции с хранилищем вне SQL-транзакции и фиксирует результат условно по актуальному token. Частичный успех и потеря ответа требуют повторной проверки и reconciliation. Удаление объекта нельзя считать завершённым, пока не учтены незаконченный multipart upload, все выданные ещё действительные права записи и поздние upload/copy-операции. `not_before` должен учитывать максимальное истечение выданных прав и запас времени; простое истечение ссылки не отзывает уже начатую операцию. Нужны повторная проверка хранилища и уборка поздно появившихся версий/незавершённых загрузок. Эта гарантия зависит от свойств хранилища и должна быть проверена на выбранной инфраструктуре; одно SQL-поле не обеспечивает её.

Если включено versioning, необходимо удалить **все подлежащие удалению версии и незавершённые multipart-загрузки**, а не только создать delete marker. Конкурентный воркер с истёкшим lease может всё ещё выполнять S3-операцию: fencing защищает запись БД, но не отменяет внешнее действие. Поэтому storage key не переиспользуется, операция удаления адресуется только устаревшему объекту/версиям, а внешние операции проектируются идемпотентными. Физическая очистка, юридическое хранение, существующие независимые привязки и политика удаления персональных данных требуют согласования.

Presigned download URL может оставаться работоспособным до истечения после Release или отзыва прав. Мгновенный отзыв не обещается; он потребовал бы отдельного механизма авторизованной выдачи потока или другого проверенного контроля на стороне хранилища. Срок, аудит и максимально допустимое окно доступа определяются контрактом.

## События, метаполя и решения до реализации

DBML фиксирует локальные сущности, ключи, метаполя и основные связи; `constraints.sql` — только часть физических ограничений. Текущая схема не доказывает 3НФ всех функциональных зависимостей или неизменяемость объекта. Проверка связи File/UploadSession/Binding, одна активная попытка на файл, полнота проверок, статус ресурсов и защита `READY` реализуются транзакционными правилами или дополнительными ограничениями после уточнения сценариев. В File и проверке намеренно повторяется storage version ID для фиксации того, какие байты проверены; равенство защищается процедурой/ограничением и тестами. ID операций находятся в UploadSession и FileBinding; их namespace, срок действия и точный API-контракт нужно определить.

События FileReady/FileRejected/FileDeleted и outbox — возможное расширение; наличие outbox в DBML не означает согласованный CDC или потребителей. Версии схем событий, retry и dedupe надо определить до реализации. Необходимо также определить TTL, retention, аудит и безопасное удаление персональных данных, правила целостности checksum, источник прав и межсервисное делегирование, устойчивость к потерянному ответу S3, лимиты и конфигурацию versioning.

Перед миграциями нужны тесты PostgreSQL и выбранного хранилища: Bind/Release/Cleanup, два параллельных Bind и отзыв последней связи, Complete/Cancel, поздний ответ storage/scanner, попытка записи после сканирования, потерянный ответ multipart, истечение lease, физическая очистка версий и поздних записей, проверка purpose и выдачи URL. Синтаксическая проверка DBML/SQL не подтверждает этих гарантий.
