# Identity Service: реализация и проектирование

Identity — частично реализованный сервис. Источник истины для PostgreSQL — `services/identity/db/migrations/*.sql`; его DBML находится в `services/identity/db/schema.dbml` и сам называет миграции источником истины. [Аудит схемы](../../data-model/identity/index.md) и [юзкейсы](use-cases.md) отделяют найденный код от планов. Схему и миграции этим документом не меняем: Identity уже имеет данные и изменение требует отдельной совместимой миграции.

## Ответственность

Identity владеет учётными записями и контактами, базовым профилем identity, password credentials, MFA-данными, OAuth-клиентами, сессиями, refresh token families, подписывающими ключами и аудитом безопасности. Candidate владеет профессиональным профилем и резюме, Company — корпоративным членством, OpenFGA/доменные сервисы — правами на ресурсы. Успешная аутентификация сама по себе не даёт прав на вакансию или отклик.

## Соответствие C4 L3

| Компонент L3 | Что установлено в репозитории |
|---|---|
| **Authentication & Registration Service** | Есть `internal/usecase/authentication` и зарегистрированные gRPC Registration/Authentication handlers. Реализация отдельных заявленных вариантов MFA требует проверки по конкретным методам. |
| **OAuth & Token Service** | Есть `internal/usecase/oauth`, gRPC handlers Authorize, ContinueAuthorization и ExchangeToken для authorization_code/refresh_token. Также есть use cases RevokeToken и GetUserInfo, но соответствующие gRPC handlers в текущем `internal/transport/grpc/oauth` не найдены. |
| Credential Security Service / Token Minting & Key Service | Код password/token и signer/verifier присутствует; наличие всех предусмотренных L3 операций управления/ротации ещё не подтверждено. |
| External Integration Adapter | C4 описывает федерацию OIDC. В просмотренных `internal/usecase`, gRPC handlers и `internal/integrations` полноценный вход через внешний IdP не найден; наличие доменных external accounts и таблицы не доказывает работающий federation flow. |
| Identity, Credential, Session, OAuth Client & Keys Repo; Authorization Transaction Repo | В `internal/repository` присутствуют соответствующие пакеты, в том числе репозитории временных authorization transaction/code. Соответствие конкретным транзакционным гарантиям требует интеграционных проверок. |
| Transactional Outbox | Есть таблица и repository outbox; доставка CDC и эксплуатационные гарантии требуют проверки окружения. |
| gRPC Server | Регистрирует Registration, Authentication, OAuth, IdentityMetadata и внутренние OAuthClientAdmin/SigningKeyAdmin. Наличие use case не означает, что он зарегистрирован как внешний endpoint. |

Это компоненты одного развёртывания. Диаграмма L3 описывает целевой состав и сценарии; расхождения с кодом требуют отдельного обновления C4 или реализации, а не изменения документации в обход фактов. Временные authorization transactions и authorization codes по L3 хранятся в Redis, а не в DBML PostgreSQL.

## Границы агрегатов

| Корень или модель | Состав и граница |
|---|---|
| Identity | Учётная запись с Email, Phone и ExternalAccount; сущности имеют собственные ID внутри модели Identity. Статус учётной записи не является состоянием Candidate. |
| IdentityProfile | Отдельный профиль identity, связанный по identity ID; не хранит карьерные сведения. |
| Password и auth state | Учётные данные пароля и состояние защиты от перебора. Хеш и счётчики хранятся в отдельных таблицах; их точную транзакционную границу определяет repository/use case. |
| Session | Одна аутентифицированная сессия со scopes и сроками/отзывом. |
| RefreshTokenFamily | Семейство и история ротации; повторное использование требует согласованного отзыва согласно реализованному сценарию. |
| OAuthClient и AuthorizationGrant | Клиент с разрешёнными redirect URI, grants и scopes; отдельный грант пользователя и его scopes. |
| MFA, RecoveryCodeSet и verification/reset challenges | Небольшие модели со своими жизненными циклами. Наличие доменной модели и таблицы не доказывает доступность полного пользовательского сценария. |
| SigningKey и ServiceAccount | Собственные модели и хранение ключевых метаданных/учётных данных. Наличие service account таблиц не доказывает доступность управления ими по API. |

Отдельные таблицы не означают отдельных application services. Регистрация и OAuth могут менять несколько агрегатов в одной локальной транзакции; бизнес-события сохраняются через outbox. Для чувствительных сценариев необходимо проверять реальный путь транзакции и обработку сбоев, а не делать вывод по C4 или одной диаграмме.

## Безопасность и интеграционные границы

Секреты не должны попадать в документацию, логи, payload событий или ответы без явного протокола. Хранение password hash, токенов, OTP, подписывающих ключей и аудита требует анализа конкретной реализации и настроек, включая ротацию и отзыв. Объявленные в C4/OIDC discovery адреса не доказывают, что все соответствующие endpoints подключены к gateway и работают. Текущая L3 описывает федеративный вход и управление сессиями шире, чем удалось подтвердить просмотром зарегистрированных handlers.

Для Candidate или других сервисов сопоставление внешних ID, право раскрытия подтверждённых контактов и реакция на отключение identity требуют отдельного контракта. Нельзя считать, что UUID профиля кандидата обязательно совпадает с identity ID. Глобальное удаление учётной записи, очистка или отзыв доступа во всех сервисах требуют отдельного согласованного процесса, а не одного локального удаления строки.

## Аудит и дальнейшие решения

При поверхностном сравнении список из 32 PostgreSQL-таблиц DBML совпал по именам с `CREATE TABLE` в миграциях. Имена колонок также сверены с базовыми CREATE TABLE; единственное отличие — `oauth_clients.consent_mode`, добавляемый последующей миграцией. Это **не проверка эквивалентности** типов, FK, CHECK, индексов, частичных индексов и всех последующих ALTER; DBML не заменяет миграции. Проверку схемы на настоящем PostgreSQL, откаты миграций и тесты конкуренции/отказов Redis необходимо проводить отдельно. Доступный use case без gRPC handler и настроенного маршрута не объявляется работающим внешним API.

До дальнейшей разработки: сверить протобуфы, handlers, gateway-маршруты и C4; определить степень готовности MFA, федерации, revoke/userinfo и сессионных API; проверить миграции против DBML и SQL-запросов с живой PostgreSQL/Redis; уточнить security events, срок хранения, выдачу и ротацию signing keys, защиту admin API и контракты с соседними сервисами. Изменять уже существующие таблицы, индексы или constraints без версионированной миграции нельзя.
