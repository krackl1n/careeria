# Candidate Service: функции и сценарии

Статус — **предлагаемые функции**, а не перечень реализованных API. За основу взяты [существующее описание сценариев Candidate в C4](../../architecture/c4/plantuml/system-context%28L1%29/full-system%28L2%29/candidate-service%28L3%29/index.md) и [проект модели Candidate](index.md). Здесь описаны цели пользователей и участников интеграции; названия операций служат рабочими идентификаторами, а не утверждённым protobuf-контрактом. Для C4 и существующего L3 потребуется отдельное обновление после согласования.

## Участники и граница

| Участник | Роль в сценариях |
|---|---|
| Кандидат | Владелец профиля, управляет своими профессиональными данными и резюме. Взаимодействует с сервисом через интерфейс платформы. |
| Рекрутер | Авторизованный представитель компании, ищет кандидатов и просматривает разрешённые данные. Корпоративная роль сама по себе не означает доступ ко всем профилям. |
| Hiring Service | Выступает инициатором согласованного межсервисного сценария подготовки данных для конкретного отклика. Полный контракт и доверенная передача контекста ещё не определены. |
| File Service | Участвует в загрузке, проверке, привязке, скачивании и освобождении файлов. Не является владельцем профиля. |
| Планировщик | Запускает восстановление незавершённых операций и очистку; это технический инициатор, а не пользователь. |
| Identity и авторизация | Предоставляют проверенную личность, контакты и решения о доступе в соответствующих сценариях. Детали их взаимодействия ещё требуют контракта. |

Граница схем — именно **Candidate Service**. Кандидат не отправляет байты файла через сервис: интерфейс загружает их непосредственно в хранилище по ограниченной ссылке File Service. Вход в аккаунт, управление компанией, сам отклик, решение о найме и выдача итогов оценки принадлежат другим контекстам. Подготовка данных для отклика не создаёт сам отклик.

## Диаграммы прецедентов

Для читаемости один контекст разделён на два вида. Овалы объединяют близкие цели; ниже они раскрыты отдельными сценариями. Связи показывают участие, но не дают разрешение: для каждой операции действуют проверки владельца, состояния и прав. Технические зависимости Identity и авторизации на диаграммах не дублируются для каждого действия.

На втором виде File Service — взаимодействующий сервис: Candidate запрашивает у него технические операции. Для сценария отклика собственная привязка файла и сохранение отклика координируются с Hiring и File Service; диаграмма не утверждает, что Candidate выполняет всю эту работу сам. Планировщик обозначает запуск фонового сценария, а не отдельный продуктовый сервис.

## Каталог сценариев

Во всех командах identity берётся из доверенного контекста. Владелец проверяется на стороне сервиса; для обычного изменения требуется ACTIVE-профиль. Операции изменения существующего агрегата проверяют его версию, а создание и внешние побочные эффекты — идемпотентность. Общие правила конкуренции и транзакций приведены в [проекте модели](index.md#transactions).

### Профиль и профессиональные данные

| ID и операция | Инициатор и условия | Действие и результат | Важное исключение |
|---|---|---|---|
| **P01 CreateProfile** | Кандидат с учётной записью, у которой нет профиля | Создаёт профиль с именем; получает ID и версию. Начальные настройки: ACTIVE, PRIVATE, HIDDEN, NOT_LOOKING. | Повтор с тем же ключом возвращает прежний результат; другой запрос для той же identity не создаёт второй профиль. |
| **P02 GetMyProfile** | Кандидат — владелец | Получает свои профиль, настройки и профессиональные данные, в том числе архивные. | Нет профиля — отсутствие ресурса; просмотр не создаёт его автоматически. Файлы и URL не возвращаются без отдельного запроса. |
| **P03 UpdateProfile** | Владелец ACTIVE-профиля | Меняет выбранные поля описания, местоположение, временную зону и ссылки; получает новую версию. | Частичное обновление различает очистку и отсутствие изменения. Статус, видимость и владельца менять через него нельзя. |
| **P04 Add / Update / RemoveExperience** | Владелец ACTIVE-профиля | Добавляет, меняет или удаляет одну запись опыта с организацией, ролью и датами. | Конец не раньше начала; NULL означает текущую работу. Пересечения разрешены; ссылка на компанию не доказывает занятость. |
| **P05 Add / Update / RemoveEducation** | Владелец ACTIVE-профиля | Управляет одной записью образования, программой и датами. | Даты валидируются, незаконченное образование возможно; запись не подтверждает квалификацию. |
| **P06 SetSkills** | Владелец ACTIVE-профиля и актуальная версия набора | Заменяет набор навыков целиком; ключи нормализуются и остаются уникальны в профиле. | Конфликт версии или ошибка одного элемента не оставляет частичной замены; уровень — самооценка. |
| **P07 UpdatePreferences** | Владелец ACTIVE-профиля | Меняет желаемые роли, условия, географию, переезд и зарплатные ожидания. | Диапазон корректен; валюта и период обязательны при указанной сумме. Очистка отличается от нуля. |
| **P08 ChangeJobSearchStatus** | Владелец ACTIVE-профиля | Явно выбирает OPEN_TO_WORK, OPEN_TO_OFFERS или NOT_LOOKING. | Статус не открывает профиль автоматически и не выводится из наличия отклика. |
| **P09 ChangeVisibility** | Владелец ACTIVE-профиля | Отдельно выбирает видимость профиля и контактов. | PRIVATE закрывает новые внешние чтения; RECRUITERS допускает лишь уполномоченных рекрутеров. Требования к заполненности перед публикацией пока не утверждены. |
| **P10 ArchiveProfile** | Владелец | Архивирует и скрывает профиль; архив остаётся доступен для собственного чтения. | Запись и новые загрузки запрещены; команда не удаляет аккаунт, историю найма или файлы. Уже начатую загрузку можно отменить. |
| **P11 RestoreProfile** | Владелец архивного профиля | Восстанавливает профиль в ACTIVE с PRIVATE, HIDDEN и NOT_LOOKING. | Прежняя публикация не включается автоматически. Повтор для текущего состояния — no-op. |

P04 и P05 используют версии соответствующей записи, P06 — версию набора навыков, P07 — версию предпочтений; общая версия профиля не заменяет эти токены. Это намеренное отличие от старого L3, где всё перечисленное менялось через профиль.

### Доступ рекрутера

| ID и операция | Инициатор и условия | Действие и результат | Важное исключение |
|---|---|---|---|
| **V01 ListDiscoverableCandidates** | Рекрутер с правом поиска | Получает страницу разрешённых ACTIVE/RECRUITERS-профилей, используя согласованные фильтры и непрозрачный cursor. | Нет контактов, файлов и гарантии точного total; доступ проверяется для ресурсов. Набор фильтров и стоимость проверок ещё нужно согласовать. |
| **V02 GetCandidateProfile** | Уполномоченный рекрутер | Получает разрешённую карточку конкретного кандидата. | PRIVATE/ARCHIVED и отсутствие права не раскрывают факт существования ресурса. Доступ к карточке не означает права скачать резюме. |
| **V03 GetCandidateContacts** | Рекрутер с отдельным разрешением, контактная видимость позволяет раскрытие | Получает разрешённые контакты через согласованное взаимодействие с Identity. | Это выделенная цель для анализа доступа, не утверждённый RPC Candidate: формат и источник выдачи контактов ещё не согласованы. При недоступности проверки доступ не расширяется. |

Участие в найме само по себе не даёт обходить приватность профиля по произвольному `application_id`: доступ к историческому представлению определяется контрактом Hiring. Для cursor-пагинации и авторизации нужно спроектировать ограниченное число проверок и продолжение по последней проверенной записи; при неполной выборке точный total не обещается.

### Резюме и файл

| ID и операция | Инициатор и условия | Действие и результат | Важное исключение |
|---|---|---|---|
| **R01 BeginResumeUpload** | Владелец ACTIVE-профиля | Создаёт резюме и первую попытку загрузки; возвращает идентификаторы и ограниченные параметры загрузки от File Service. | Повтор с тем же ключом восстанавливает операцию. Ответ File Service может потеряться; отсутствие ответа не означает отсутствие файла. |
| **R02 BeginResumeVersionUpload** | Владелец ACTIVE Resume | Начинает новую версию существующего резюме с новым номером и operation ID. | Существующая READY-версия остаётся текущей во время загрузки и при неудаче. |
| **R03 CompleteResumeUpload** | Владелец, профиль ACTIVE, попытка не отменена | Запрашивает подтверждение File Service и фиксирует CHECKING, READY или безопасный отказ. Первую READY-версию можно выбрать текущей. | Сам факт загрузки байтов не делает файл READY; новые версии не активируются автоматически. Файл и binding должны быть подтверждены File Service. |
| **R04 Get / ListResumes** | Владелец; рекрутер — с отдельным правом | Получает метаданные разрешённых резюме. Владелец видит состояния своих попыток. | Рекрутер не видит удалённые резюме и незавершённые версии. Список не должен выдавать URL на каждый файл. |
| **R05 RenameResume** | Владелец ACTIVE Resume | Меняет название и получает новую версию агрегата. | Не меняет файл и не создаёт версию документа. |
| **R06 ActivateResumeVersion** | Владелец ACTIVE Resume | Явно делает выбранную READY-версию этого резюме текущей. | Чужая, незавершённая или отклонённая версия недопустима; уже выбранная — no-op. |
| **R07 SetPrimaryResume** | Владелец ACTIVE-профиля | Выбирает одно ACTIVE-резюме с текущей READY-версией как основное. | Это предпочтение не даёт права скачивания и не меняет ранее отправленные отклики. |
| **R08 GetResumeDownloadURL** | Владелец или рекрутер с отдельным разрешением | Получает краткоживущую ссылку на разрешённый READY-документ от File Service. | Нельзя выдать ссылку на чужой, удалённый или неготовый файл; ранее выданную ссылку мгновенно отозвать может быть невозможно — срок действия требует решения. |
| **R09 CancelResumeUpload** | Владелец, включая владельца архивного профиля | Отменяет незавершённую попытку и ставит задачу освобождения привязки. | Позднее подтверждение не возвращает попытку в READY; очистка должна восстановить потерянный результат Begin. |
| **R10 DeleteResume** | Владелец ACTIVE-профиля | Помечает резюме удалённым, снимает выбор основного при необходимости и запускает освобождение привязок профиля. | Сохранённый отклик может иметь собственную привязку; его документ этой командой не удаляется. Полное удаление персональных данных — отдельный процесс. |
| **R11 ReconcileAndCleanup** | Планировщик | Согласует зависшие загрузки и с lease/retry освобождает ненужные привязки. | Выполняется и для архивного профиля. Внешняя операция и SQL не атомарны; нужна идемпотентность. |

### Межсервисный сценарий

| ID и операция | Инициатор и условия | Действие и результат | Важное исключение |
|---|---|---|---|
| **I01 PrepareApplicationData** | Hiring в доверенном контексте кандидата и конкретного отклика | Получает согласованный минимальный снимок профиля и идентификатор выбранной READY-версии резюме. | Это проектируемое взаимодействие, не реализованный RPC и не создание отклика. Hiring должен обеспечить отдельную устойчивую привязку файла с File Service; порядок, авторизация, промежуточные состояния и компенсация ещё не согласованы. |

История отклика должна ссылаться на конкретную версию и снимок, чтобы последующее редактирование профиля, выбор другого основного резюме или новой версии не меняли отправленные данные. Правила сохранения и отзыва доступа к историческому файлу требуют отдельного решения.

## Ошибки и общие правила

Для реализации различаются: неаутентифицированный запрос; недоступный ресурс; неверные поля; недопустимое состояние; конфликт версии; повтор с другим содержимым; недоступная зависимость; файл ещё проверяется, отклонён или загрузка истекла. Названия ошибок и mapping в транспортный контракт пока не утверждены. При сбое проверки прав нельзя автоматически разрешать доступ.

Команда изменения состояния и её интеграционное событие фиксируются локально атомарно. Межсервисные вызовы происходят вне удерживаемой SQL-блокировки; восстановление использует стабильные operation ID, идемпотентность и повторные проверки. События не содержат файлы, контакты, содержимое профиля или временные URL.

## Что согласовать перед API и C4

- Состав данных и минимальную заполненность для публикации; фильтры поиска, лимиты, сортировку и условия видимости контактов.
- Разрешения рекрутера, точный путь получения контактов и принцип доступа к документу в контексте существующего отклика.
- Поддерживаемые File Service операции восстановления Begin, проверки безопасности, привязки и повторной выдачи короткоживущих URL; допустимые типы и размеры файлов.
- Контракт I01: кому и какие поля отдавать, как привязать файл к отклику, обработать сбои, отзыв и удаление данных.
- Модель бизнес-событий, версии API, сроки хранения идемпотентности и семантику полного удаления профиля.

Импорт кандидатов компанией, подтверждение опыта и навыков, автоматический разбор файла, рекомендации и коммуникация с кандидатом в этот каталог не включены; при появлении подтверждённой потребности им нужны отдельные сценарии и владельцы.
