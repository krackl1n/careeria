# Hiring Service — компоненты L3

Hiring Service владеет откликами, FSM этапов найма, интервью, офферами и историей переходов. Диаграмма раскрывает одноимённый контейнер L2. API Gateway, Hiring DB, Kafka, Schema Registry, OpenFGA и LiveKit принадлежат Careeria; готовая инфраструктура обозначена общим серым тегом. Событийный маршрут CDC раскрыт в L2 и не дублируется здесь.

## Сценарии и домен

gRPC Server направляет команды и запросы в бизнес-сервисы соответствующих модулей:

- Application Service — отклики, смена этапов, история воронки и внешняя синхронизация.
- Interview Service — расписание, участники, завершение интервью и feedback.
- Offer Service — создание, отправка, принятие, отзыв и истечение офферов.
- Conference Service — комнаты конференций и их согласование с интервью через LiveKit Client.

Это прикладные компоненты внутри контейнера Hiring Service, а не отдельные микросервисы. Разделение commands/queries логическое: отдельная CQRS-база не вводится.

Hiring Domain содержит компактные агрегаты Application, Interview и JobOffer, FSM и межагрегатные политики. Только Hiring Service меняет этап Application. Завершённое интервью и feedback проверяются перед выдачей оффера, а внешняя синхронизация учитывает версии и терминальные состояния. Прикладные сценарии проверяют права через Authorization Client и Go SDK OpenFGA; доменное ядро не зависит от SDK, gRPC или PostgreSQL.

Events Consumer читает Avro-события из Kafka, получает схемы в Schema Registry и вызывает Application Service. HR-события поступают через Integration Service, а результаты оценивания — через событийную шину. Offer Expiration Worker вызывает Offer Service для истечения офферов.

## Транзакции и интеграции

Tx Manager передаёт одну PostgreSQL-транзакцию репозиториям и outbox. Изменение агрегатов, история перехода, отметка обработки входящего события и исходящие события фиксируются атомарно. При принятии оффера Offer Service согласует изменение этапа через Application Service в общем транзакционном контексте. Репозитории не начинают независимые транзакции. Повторная доставка Kafka-события не должна повторять бизнес-операцию; offset подтверждается после коммита.

События публикуются по пути `Hiring DB → Debezium → Kafka`, включая топик `careeria.hiring.events`. Прямой публикации из прикладного сервиса нет. Notification Service и AuthZ Synchronization Service остаются потребителями этих событий, а не синхронными зависимостями Hiring Service.

Conference Service использует LiveKit Client и отражает существующую L2-связь создания комнат интервью. Проверки OpenFGA и вызовы LiveKit выполняются вне бизнес-транзакции. Сбой сохранения интервью после создания комнаты требует повторяемого сценария и компенсации; конкретный протокол восстановления предстоит уточнить при реализации.

## Что уточнить в спецификации перед реализацией

- FSM упоминает OFFER_REJECTED, но SQL и Protobuf его не содержат. Нужен единый набор этапов и согласованные терминальные состояния.
- Уникальность `(vacancy_id, candidate_id)` в SQL запрещает любой повторный отклик, хотя текст запрещает только второй активный. Ограничение следует согласовать с бизнес-правилом.
- Схеме нужны данные участников интервью и механизм дедупликации/версий внешних событий, которые описаны в сценариях, но пока отсутствуют в SQL-примере.
