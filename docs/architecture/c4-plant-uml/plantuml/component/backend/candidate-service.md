# Candidate Service — компоненты L3

Candidate Service владеет профилем кандидата, его профессиональным описанием, опытом, образованием, навыками, карьерными предпочтениями, статусом поиска работы и каталогом резюме. **Содержимое файлов резюме хранится в S3-совместимом Object Storage, остальные данные — в Candidate DB (PostgreSQL).** Доступ к файлам выполняется через общий File Service, уже существующий в L2.

```plantuml
@startuml
!include architecture/c4-plant-uml/plantuml/component/backend/candidate-service.puml
@enduml
```

## Границы и статус проекта

Это предлагаемая целевая архитектура и каталог сценариев, не описание уже реализованных RPC. Названия команд ниже задают проектируемый контракт; protobuf, миграции и обработчики ещё предстоит реализовать. В отличие от предыдущих сервисов, отдельная исходная спецификация кандидатов не предоставлена: ограничения и статусы здесь предложены явно.

В одном backend-контейнере выделены два бизнес-компонента:

- **Candidate Profile Service** — профиль и его вложенные профессиональные данные, статус поиска, видимость, личные и доступные рекрутерам представления.
- **Resume Service** — самостоятельный агрегат Resume: загрузки, неизменяемые версии файлов, основное резюме и доступ к документу.

Это не два микросервиса. Оба используют Candidate DB и один внешний контракт CandidateService. Не нужны отдельные application services для каждого поля, навыка или перехода статуса. Жизненный цикл и инварианты закреплены в доменных агрегатах, а не в gRPC-обработчиках или repository.

| Данные / действие | Владелец | Граница |
|---|---|---|
| Описание кандидата, профессиональные контакты, опыт, образование, навыки, предпочтения | Candidate Service | Не изменяет учётную запись или credentials. |
| Статус поиска работы и видимость профиля | Candidate Service | Не является статусом отклика или интервью. |
| Названия резюме, версии, основной документ, принадлежность кандидату | Candidate Service | Сохраняет file ID и проверенные метаданные, не бинарные файлы. |
| Байты файла, upload session, проверка типа/размера, антивирус, S3 object key, presigned URL | File Service / Object Storage | Сервис кандидатов не принимает произвольный S3 key от пользователя. |
| Регистрация, login, пароли, подтверждение email и блокировка аккаунта | Identity Service | user ID берётся из доверенного identity context. |
| Отклик, его этап, интервью, оффер и снимок данных при отклике | Hiring Service | Изменение профиля не переписывает исторический отклик. |
| Диалоги с HR, сообщения и вложения чата | Communication Service | Не хранятся в Candidate DB. |
| Доставка уведомлений | Notification Service | Candidate Service записывает события в outbox, не отправляет письма. |

Внутренние компоненты и их связи объявлены только в `candidate-service.puml`. `model/candidate-elements.puml` содержит общие имя контейнера и Candidate DB, используемые L2/L3. File Service, Object Storage и OpenFGA тоже переиспользуются из общих объявлений. Все находятся внутри Careeria; серый цвет обозначает готовую инфраструктуру, а не внешнюю систему. Kafka, Schema Registry и Debezium не раскрываются на этой L3: сервис не является их непосредственным клиентом, здесь показан transactional outbox.

## Элементы диаграммы

### Внутренние компоненты

| Элемент | Технология / слой | Ответственность | Зависимости |
|---|---|---|---|
| gRPC Server | Go / gRPC | Проверяет структуру запроса, передаёт identity context, request ID и ключ идемпотентности, преобразует прикладные ошибки. Не выполняет бизнес-проверки вместо сервисов. | Candidate Profile Service, Resume Service |
| Candidate Profile Service | Go Application Service | Координирует создание и изменение профиля, профессиональные данные, статусы и доступные представления. Вызывает доменные методы CandidateProfile. | Authorization Client, Candidate Repo, Transactional Outbox |
| Resume Service | Go Application Service | Координирует загрузку/подтверждение, версии, выбор основного резюме, выдачу доступа и удаление. Проверяет владельца и состояние Resume. | Authorization Client, Resume Repo, File Service Client, Transactional Outbox |
| Authorization Client | Go / OpenFGA SDK | Адаптирует ReBAC-проверки профиля и резюме. Не решает, готов ли файл, допустим ли статус или какие поля показывать. | OpenFGA |
| Candidate Repo | Go / pgx, sqlc | Загружает и сохраняет CandidateProfile, опыт, образование, навыки и предпочтения; выполняет ограниченные выборки. | Candidate DB |
| Resume Repo | Go / pgx, sqlc | Сохраняет Resume/ResumeVersion, идемпотентные операции и cleanup jobs; обеспечивает конкурентный захват jobs. | Candidate DB |
| File Service Client | Go / gRPC | Создаёт upload session, получает проверенное состояние файла, привязывает/освобождает ресурс, запрашивает download URL. Ограничивает timeout и безопасные повторы. | File Service |
| Transactional Outbox | Go / pgx, sqlc | Сохраняет события в той же SQL-транзакции и на том же соединении, что изменение агрегата. | Candidate DB |
| Resume Cleanup Worker | Go Background Worker | Выполняет отложенное освобождение файлов, повторы и reconciliation незавершённых загрузок. Не удаляет S3 object напрямую. | Resume Repo, File Service Client |

Repository и outbox получают один transaction handle от прикладного слоя; это не несколько независимых commit. Tx Manager как отдельный компонент на данной диаграмме не выделен. Его реализация может быть общей технической обвязкой `WithinTransaction`, без нового бизнес-сервиса.

## Доменная модель и хранение

| Сущность | Основные данные | Инварианты |
|---|---|---|
| CandidateProfile | candidate ID, уникальный user ID, имя для показа, headline, about, location, timezone, профессиональные ссылки, lifecycle, search status, visibility, contact visibility, version, timestamps | Один профиль на user ID. Только разрешённые поля; нельзя подменить user ID. Статус поиска не меняется как побочный эффект обычного редактирования. |
| WorkExperience | ID, candidate ID, компания как текст и необязательный company ID, должность, описание, даты, isCurrent | Начало не позже конца; текущий опыт не имеет даты окончания. Указание компании не создаёт корпоративного членства. |
| Education | ID, candidate ID, организация, программа/степень, специальность, даты | Связь только с данным профилем; корректные даты. Несколько записей разрешены. |
| CandidateSkill | candidate ID, нормализованный skill key, отображаемое имя, необязательный уровень | Уникальность навыка в профиле; self-reported уровень не равен подтверждённому результату Assessment. |
| CareerPreferences | желаемые роли, уровни, employment types, work formats, locations, relocation, зарплатные ожидания и валюта | Диапазон компенсации валиден; валюта и период указаны; предпочтения не означают принятие оффера. |
| Resume | resume ID, candidate ID, название, язык, ACTIVE/DELETED, activeVersionId, isPrimary, version, timestamps | У кандидата несколько резюме; не более одного основного. Основным может быть только ACTIVE с READY-версией. |
| ResumeVersion | version ID, resume ID, порядковый номер, file ID, upload operation ID, состояние, проверенные MIME/size/checksum, timestamps | Файл версии после READY неизменяем. Новый файл — новая версия, а не перезапись S3 key старой. file ID принадлежит владельцу и назначению resume. |
| ResumeCleanupJob | job ID, binding ID/file ID, причина, lease owner/until, attempts, nextAttemptAt, lastError, state | Освобождение идемпотентно; несколько workers не должны выполнять один job одновременно без lease. |
| OutboxEvent | event ID, aggregate ID/type/version, event type, schema version, occurredAt, минимальный payload | Уникальный event ID; состояние и события фиксируются атомарно. |

Профиль с опытом/образованием/навыками сохраняется как агрегат CandidateProfile. Resume — отдельный агрегат, чтобы загрузка файла не блокировала редактирование описания. Межагрегатный инвариант «одно основное резюме» обеспечивается SQL-транзакцией и частичным уникальным индексом по candidate ID для `is_primary = true AND lifecycle = 'ACTIVE'`, а не одним предварительным SELECT.

Предлагаемые таблицы: `candidate_profiles`, `candidate_experiences`, `candidate_educations`, `candidate_skills`, `candidate_preferences`, `resumes`, `resume_versions`, `resume_cleanup_jobs`, `idempotency_keys`, `outbox`. Внутри Candidate DB используются внешние ключи и ограничения. Между сервисами — только идентификаторы и согласованные контракты, без cross-database FK.

В S3 — только бинарный документ. Candidate DB не хранит файл, base64, постоянный публичный URL, credentials или копию upload session. S3 key и технические ссылки принадлежат File Service; Candidate Service использует стабильный file ID. Имя файла от клиента — недоверенная отображаемая строка, не путь хранения.

## Статусы и видимость

Статусы разделены по смыслу и не объединены в одно поле `status`.

| Ось | Предлагаемые значения | Правило |
|---|---|---|
| Жизненный цикл профиля | ACTIVE, ARCHIVED | Новый профиль ACTIVE. Архивирование скрывает его от рекрутеров; восстановление не включает прежнюю публикацию автоматически. |
| Статус поиска | OPEN_TO_WORK, OPEN_TO_OFFERS, NOT_LOOKING | Кандидат меняет явно. Начальный NOT_LOOKING; наличие профиля или нового резюме не является согласием на поиск. |
| Видимость профиля | PRIVATE, RECRUITERS | По умолчанию PRIVATE. RECRUITERS означает доступ уполномоченным рекрутерам, а не всем пользователям или интернету. |
| Видимость контактов | HIDDEN, AUTHORIZED_RECRUITERS | По умолчанию HIDDEN. Доступ к карточке не означает доступ к контактам или файлам резюме. |
| Жизненный цикл Resume | ACTIVE, DELETED | Удаление прекращает новые выдачи документа из профиля. Терминальное состояние; восстановление удалённого файла не обещается. |
| Состояние ResumeVersion | UPLOADING, CHECKING, READY, REJECTED, EXPIRED | Только READY разрешает скачивание и выбор основной версии. REJECTED/EXPIRED — терминальные для этой попытки. |

Переходы версии: `UPLOADING → CHECKING → READY / REJECTED`, а незавершённая загрузка по истечении допустимого срока переходит в EXPIRED. Полная загрузка байтов ещё не делает версию READY: File Service подтверждает существование объекта, реальный тип/размер и успешную проверку безопасности. Если проверка ещё идёт, CompleteResumeUpload возвращает CHECKING; повторный вызов или GetResume обновляет статус через проверенное состояние File Service. Cleanup Worker периодически reconciles незавершённые операции, поэтому пользователь не обязан держать вкладку открытой.

Доменные методы CandidateProfile управляют состоянием/видимостью и не позволяют архивному профилю стать доступным рекрутерам. Восстановление переводит его в ACTIVE с PRIVATE, HIDDEN и NOT_LOOKING; публикация выполняется отдельным явным действием. Archive не удаляет данные и не закрывает отклики в Hiring Service.

### 1. CreateCandidateProfile — создать профиль

**Инициатор и вход:** аутентифицированный пользователь, минимальные поля имени для показа; user ID определяется из identity context, не из тела. Операция не регистрирует новую учётную запись.

**Проверки и выполнение:** Candidate Profile Service проверяет допустимость полей, уникальность user ID, создаёт CandidateProfile с ACTIVE/NOT_LOOKING/PRIVATE/HIDDEN. Профиль и CandidateProfileCreated сохраняются одной SQL-транзакцией. Конкурентное создание останавливает уникальный индекс, а не только предварительная проверка.

**Результат и повтор:** возвращаются candidate ID и version. Повтор с тем же ключом и тем же payload возвращает исходный результат; тот же ключ с другим payload — конфликт. Если профиль уже есть без совпадающего ключа, возвращается AlreadyExists, после чего клиент может вызвать GetMyCandidateProfile. На bootstrap владелец проверяется по доверенному user ID и записи в своей БД, а не через ещё отсутствующие OpenFGA tuples.

### 2. GetMyCandidateProfile — получить собственный профиль

**Вход:** identity context; необязательные параметры включения вложенных коллекций. По уникальному user ID находится профиль, возвращаются полные профессиональные данные, настройки, lifecycle, search status и version, включая архивный профиль. Файлы резюме и download URL в ответ автоматически не включаются.

**Ошибки:** отсутствие профиля — NotFound; это не команда его неявного создания. Сам просмотр не генерирует событие изменения. Ownership проверяется внутри прикладного сервиса по текущему user ID, даже если gateway уже проверил JWT.

### 3. UpdateCandidateProfile — изменить описание

**Вход:** candidate ID, expected version, field mask и значения имени, headline/about, location/timezone, профессиональных контактов и ссылок. Маска различает «не менять» и «очистить»; lifecycle/search status/visibility не доступны через обычный patch.

**Проверки:** владелец, ACTIVE, лимиты текста, формат контактов/ссылок и допустимые URL schemes. Ссылки не используются для серверной загрузки произвольного URL. Изменение контактного email не изменяет Identity credentials и не получает признак подтверждённого login email.

**Выполнение и результат:** доменный метод обновляет только перечисленные поля; repo делает optimistic update, outbox сохраняет CandidateProfileUpdated в той же транзакции. Несовпадение version — конфликт, клиент перечитывает данные; silent last-write-wins запрещён. Ответ содержит новое представление/version.

### 4. Add / Update / RemoveExperience — опыт работы

**Вход:** candidate ID, expected profile version, поля записи; для update/remove — experience ID. Add создаёт ID сервером, update не переносит запись в чужой профиль.

Сервис проверяет владельца, ACTIVE, обязательные поля, интервалы дат и правило текущей работы. Обновление/удаление выполняется по паре candidate ID + experience ID. Несколько одновременных мест работы разрешены, если продукт не установит иное; пересечение дат само по себе не ошибка. Company ID — ссылка, а не доказательство работы или членства.

Коллекция меняется через агрегат и фиксируется вместе с новой version и CandidateProfileUpdated. Ошибка одной записи не оставляет частичное изменение. Повтор Add с тем же idempotency key не создаёт второй опыт; Remove отсутствующей записи возвращает согласованный NotFound, повтор исходной команды восстанавливается из записи идемпотентности.

### 5. Add / Update / RemoveEducation — образование

**Вход:** профиль, expected version, организация, программа/степень, специальность и даты; для изменения/удаления — education ID. Проверяются владелец, ACTIVE, принадлежность записи и корректность интервала; незавершённое обучение допускается без end date.

Записи нескольких программ разрешены. Service вызывает доменные методы коллекции, атомарно сохраняет обновление и CandidateProfileUpdated. Это заявленные кандидатом данные, без автоматической верификации диплома или нового assessment. Конкурентные изменения и повторы обрабатываются как у опыта.

### 6. SetCandidateSkills — изменить навыки

**Вход:** полный новый набор навыков и expected profile version. Явно выбирается семантика replace-set, а не неясная смесь append/patch. Для клиента, добавляющего один навык, требуется получить текущий набор и сохранить с version.

Сервис проверяет владельца и ACTIVE, нормализует ключи по единому правилу, устраняет дубликаты, валидирует уровни и лимит количества. Удаление старых и вставка новых строк выполняются в одной транзакции с profile version и событием. Оценки Assessment Service не принимаются как произвольные поля self-reported skill. Ошибка нормализации/конфликт не приводит к частичной замене.

### 7. UpdateCareerPreferences — предпочтения

**Вход:** field mask, desired roles/seniority, форматы работы, типы занятости, география, relocation и зарплатные ожидания с валютой/периодом. Неуказанная компенсация разрешена; нижняя граница не больше верхней, значения неотрицательные. География и relocation — разные поля.

Сервис проверяет владельца, ACTIVE и version, вызывает доменный метод, атомарно сохраняет предпочтения и CandidatePreferencesUpdated. Команда не меняет status поиска, не подбирает вакансию синхронно и не принимает оффер. Удаление ожиданий должно быть явным очищением, а не значением ноль по умолчанию.

### 8. ChangeJobSearchStatus — статус поиска

**Вход:** одно из OPEN_TO_WORK / OPEN_TO_OFFERS / NOT_LOOKING и expected version. Владелец ACTIVE-профиля вызывает доменный ChangeJobSearchStatus. Между этими состояниями разрешены явные переходы; no-op не создаёт новое доменное событие.

Статус сохраняется с CandidateJobSearchStatusChanged. OPEN_TO_WORK не открывает приватный профиль; RECRUITERS не означает, что кандидат активно ищет. Статус не выводится из откликов, количества резюме, оффера или наличия employment. Notification/поисковые проекции могут обработать событие асинхронно, но не являются источником этого поля.

### 9. ChangeProfileVisibility — видимость

**Вход:** visibility, contact visibility, expected version. Владелец выбирает PRIVATE либо RECRUITERS и отдельную политику контактов. Публикация для рекрутеров требует ACTIVE и минимально заполненного профиля: предлагаем имя, headline и хотя бы одну запись опыта/образования либо непустое профессиональное описание. Точный лимит заполненности — продуктовая настройка.

Состояние и CandidateVisibilityChanged сохраняются атомарно. При PRIVATE сервис немедленно запрещает новые recruiter reads/downloads по состоянию в PostgreSQL, не ожидая обновления OpenFGA. Открытие требует одновременно текущей видимости и актуального разрешения; временный лаг проекции не расширяет доступ. Настройка контактов не раскрывает их в событиях или списках.

### 10. GetCandidateProfile — просмотр другим пользователем

**Вход:** candidate ID; инициатор берётся из identity context. Владелец получает собственное представление. Рекрутеру сервис проверяет ACTIVE, RECRUITERS, разрешение OpenFGA и возвращает разрешённые поля; контакты фильтруются отдельно. Чужой PRIVATE/ARCHIVED возвращается как недоступный ресурс без раскрытия факта существования.

Нельзя вернуть полный объект и рассчитывать, что frontend скроет контакты. Резюме перечисляются только в рамках отдельного разрешения; сам доступ к профилю не выдаёт download URL. Контекст просмотра участника найма реализуется Hiring Service через разрешённый snapshot/договорённый resource grant, а не обход PRIVATE на основании переданного клиентом application ID.

### 11. ListDiscoverableCandidates — выборка для рекрутера

**Вход:** ограниченные фильтры по навыкам, location/work format, статусу поиска, cursor и bounded page size. Инициатор должен иметь право recruiter discovery. Service выбирает только ACTIVE/RECRUITERS, применяет resource permissions и возвращает безопасные карточки без контактов/файлов.

Cursor основан на стабильной паре sort key + candidate ID; OFFSET не является контрактом. Нельзя сначала пагинировать сырую выборку, затем отфильтровать запрещённое и выдать неправильный total/пустые страницы: репозиторий читает кандидатов порциями, сервис набирает доступную страницу и ограничивает работу; если доступных записей меньше, возвращает продолжение по последней проверенной записи. Cursor непрозрачный и связан с фильтрами. Exact total не обещается.

В первой версии используются PostgreSQL и индексы; отдельный search engine не добавлен. При недоступности авторизации доступ закрывается, а не открывается всем. Дедлайны и максимальное число проверок ограничивают стоимость запроса; полнотекстовый поиск и рекомендации — отдельное развитие, не скрытая обязанность этого юзкейса.

### 12–13. Archive / RestoreCandidateProfile — архивирование и восстановление

**Вход:** candidate ID и expected version. Владелец архивирует профиль доменным методом: lifecycle становится ARCHIVED, новые чужие просмотры и скачивания блокируются. Собственное чтение доступно, изменения профессиональных данных и начало новых загрузок запрещены. Уже начатую загрузку можно отменить; завершить и активировать в архиве нельзя. Истёкшие попытки обработает worker.

Archive сохраняет CandidateProfileArchived, но не удаляет файлы, не блокирует login, не удаляет диалоги и не отзывает отклик/офер. Restore сохраняет CandidateProfileRestored и возвращает ACTIVE/PRIVATE/HIDDEN/NOT_LOOKING. Повторные команды того же состояния — no-op. Возвращение прежней открытости без отдельного согласия запрещено.

## Сценарии резюме

### 14. BeginResumeUpload — создать резюме и начать загрузку

**Вход:** candidate ID, название резюме, язык, заявленные filename/MIME/size и idempotency key. Проверяются владелец, ACTIVE-профиль, лимит резюме/загрузок и политика файлов. Предлагаемый стартовый allowlist — PDF/DOCX до 10 MiB; это конфигурируемое продуктовое ограничение, не уже установленный контракт. Разрешение расширения не заменяет анализ содержимого и антивирус.

**Порядок:** Resume Service сначала сохраняет pending Resume/ResumeVersion и устойчивый operation ID. После commit вызывает File Service BeginUpload с owner, purpose=resume, binding target=version ID и тем же operation ID. File Service возвращает file ID, upload session, presigned URL/параметры и срок действия. Метаданные операции сохраняются; клиент передаёт байты непосредственно в приватное S3-хранилище по этой ограниченной ссылке. На L3 этот пользовательский data path не раскрыт как внутренний компонент; он отмечен в L2 и описан здесь.

**Сбой и повтор:** SQL и S3 не образуют общую транзакцию. Timeout File Service не создаёт второе резюме при retry: возвращается/восстанавливается та же операция. Если ответ File Service потерян, запрос по operation ID возвращает созданную session, а не новую загрузку. Незавершённая запись остаётся resumable до expiry; worker reconciles её. Upload URL разрешает только выделенный объект/операцию и ограниченный размер, не доступ ко всему bucket.

### 15. CompleteResumeUpload — подтвердить документ

**Вход:** resume ID, version ID и operation ID, но не произвольный object key. Владелец ACTIVE-профиля подтверждает свою UPLOADING/CHECKING-версию. File Service проверяет завершённость объекта, фактический size/type/checksum, владельца, purpose и результат сканирования. Клиентские MIME/checksum не становятся доверенными автоматически.

**Выполнение:** незавершённый upload остаётся UPLOADING с корректной ошибкой; сканирование — CHECKING; отказ безопасности — REJECTED; пригодный файл — READY. Привязка файла к версии должна быть устойчивой и идемпотентной в File Service до SQL-фиксации READY. Только после этого Resume Repo фиксирует проверенные метаданные с ResumeVersionReady в outbox. Для первого файла эта версия становится activeVersion; новый файл существующего резюме не заменяет текущую версию автоматически.

**Межсервисный сбой:** если File Service закрепил файл, но SQL не завершился, повтор/reconciliation восстанавливает READY по operation/binding ID. Файл с pending binding нельзя удалять как «бесхозный» до истечения согласованного lease и проверки операции. Для отмены/expiry создаётся cleanup job. Это предлагаемое требование к контракту File Service, а не заявленная уже реализованная гарантия.

### 16. GetResume / ListResumes — метаданные

Владелец получает свои ACTIVE-резюме, версии, текущую/основную отметку и pending/rejected статусы с безопасной причиной отказа. Другому пользователю разрешается только доступное ACTIVE-резюме с READY-версией после проверки профиля и отдельного download/view permission. DELETED и pending versions не появляются в публичной выборке.

List использует bounded cursor pagination. Download URL не генерируется заранее для каждой строки. GetResume может запросить File Service для согласования конкретной незавершённой версии; обычный список не должен выполнять неограниченный N+1 сетевых вызовов. Утечки object key, антивирусных внутренних логов и файлов чужого владельца запрещены.

### 17. RenameResume — название документа

**Вход:** resume ID, новое непустое название и expected version. Сервис проверяет владельца, ACTIVE-профиль и ACTIVE Resume, обновляет доменную метаинформацию с ResumeMetadataUpdated. Не перемещает S3 object и не заменяет содержимое файла. Конкурентный rename/удаление обрабатывается через version; повтор не создаёт версию файла.

### 18. BeginResumeVersionUpload — новый файл

**Вход:** resume ID, expected version, характеристики нового файла и idempotency key. После авторизации создаётся новая ResumeVersion в UPLOADING с уникальным ordinal/operation ID, далее действует тот же безопасный протокол Begin/Complete.

Текущая READY-версия остаётся доступной во время загрузки и при отказе сканирования нового файла. Старый file ID/S3 object не перезаписывается. Можно ограничить число одновременных pending versions настройкой; конкурентные попытки не получают одинаковый номер. ResumeVersionReady не переключает activeVersion автоматически: нужен ActivateResumeVersion, чтобы не менять документ, пока кандидат его не выбрал.

### 19. ActivateResumeVersion — выбрать текущую версию

**Вход:** resume ID, version ID и expected Resume version. Владелец ACTIVE-профиля выбирает READY-версию того же ACTIVE Resume. Domain method меняет activeVersionId, repository/outbox атомарно сохраняют ResumeActiveVersionChanged.

Попытка выбрать CHECKING/REJECTED/EXPIRED, чужую версию или DELETED Resume отклоняется. Старые версии не уничтожаются этой командой; снимки откликов продолжают ссылаться на конкретную версию. Повтор выбора текущей версии — no-op. Количество и retention старых версий требуют отдельной политики; без неё worker не удаляет все «неактивные» документы.

### 20. SetPrimaryResume — основное резюме

**Вход:** resume ID и expected version/токен конкурентного выбора кандидата. Сервис проверяет владельца, ACTIVE-профиль, ACTIVE Resume и READY activeVersion. В одной транзакции блокирует изменение primary для данного candidate ID, снимает прежнюю отметку, ставит новую и записывает PrimaryResumeChanged. Уникальный индекс служит последней защитой; две параллельные команды не оставляют два основных документа.

Начальная загрузка не делает резюме основным без явной команды. Основное — предпочтение профиля, не разрешение для recruiter download и не замена резюме в уже отправленных откликах. Чтобы отличать устаревший выбор, предлагается отдельный `primary_selection_version` на уровне кандидата в таблице управления резюме; менять CandidateProfile ради этого не требуется.

### 21. GetResumeDownloadURL — доступ к файлу

**Вход:** resume ID и конкретная version ID либо запрос текущей версии. Сервис заново проверяет текущие ownership/lifecycle/visibility/resource permission, READY и право на выбранную версию; произвольный file ID из тела не используется. Для чужого пользователя по умолчанию доступна только активная версия, а не весь архив.

File Service получает доверенный resource binding и выдаёт краткоживущую presigned download URL с безопасным filename и сроком действия. Ответ не кешируется как публичная страница. Proposed TTL — до 5 минут, согласуется общей политикой File Service; ссылки не пишутся в события, аналитику или логи.

После смены видимости новые ссылки запрещены немедленно. Уже выданная S3-ссылка может действовать до expiry: если требуется мгновенный отзыв, понадобится другой механизм выдачи/проксирования, а не обещание, что OpenFGA отзовёт готовую URL. Выдача проверяется и аудитируется, но сам переход по прямой ссылке не является SQL-транзакцией Candidate Service.

### 22. CancelResumeUpload — отменить попытку

**Вход:** version ID и operation ID. Владелец может отменить свою UPLOADING/CHECKING-версию, в том числе в архивном профиле. В предлагаемой модели отменённая попытка помечается EXPIRED с reason=CANCELLED, но уже READY-файл не удаляется этой командой.

В транзакции версия закрывается и создаётся cleanup job для upload/binding. Если новый Resume ещё не получил READY-версии, он остаётся без активного документа до нового upload или DeleteResume. Основное и прежняя текущая версия не меняются. Cancel и Complete конкурируют по версии/состоянию: только один допустимый переход выигрывает; проигравший не выдаёт READY после отмены.

### 23. DeleteResume — удалить из профиля

**Вход:** resume ID, expected version и idempotency key. Владелец может удалить документ и в архивном профиле. Resume становится DELETED; activeVersion перестаёт выдаваться, primary отметка снимается без автоматического выбора другого документа. Все upload sessions/файловые bindings данного Resume получают cleanup jobs; ResumeDeleted и изменение primary записываются в той же SQL-транзакции.

**Результат:** документ уже недоступен для новых запросов, физическое освобождение файлов асинхронно. Нельзя сначала удалить S3 object, затем пытаться изменить БД: это оставит READY-метаданные на отсутствующий файл при ошибке SQL. File Service освобождает только binding профиля; файл не уничтожается, если отдельный binding удерживает его для истории найма. Повтор Delete по исходному ключу возвращает исходный результат, не создаёт новые jobs.

### 24. ReconcileAndCleanupResumes — фоновая надёжность

Worker ограниченными порциями захватывает due jobs через `FOR UPDATE SKIP LOCKED`, сохраняет lease и освобождает SQL-транзакцию **до** сетевого вызова. Затем идемпотентно освобождает binding/session через File Service и завершает job отдельной короткой транзакцией с проверкой lease token. Ответ «уже освобождён» считается успешным.

Timeout/недоступность дают backoff с jitter и новым nextAttemptAt. Истёкший lease позволяет продолжить после падения процесса; старый worker не завершает job нового владельца. Постоянные ошибки попадают в FAILED с сигналом оператору и возможностью повторного запуска, а не тихо исчезают. Политика максимального числа попыток/ручного восстановления задаётся конфигурацией.

Reconciliation также проверяет pending upload operations по operation ID: восстанавливает session/file ID после потерянного ответа, переводит проверенную версию в READY/REJECTED либо истёкшую в EXPIRED и планирует освобождение. Перед каждым финальным переходом проверяет, что Resume не удалён, профиль не архивирован для активации и операция не отменена. Решение о физическом удалении S3 object принимает File Service с учётом других bindings, retention и безопасности. Worker не является антивирусом, OCR или PDF-парсером.

## Транзакции, безопасность и интеграция

### Авторизация внутри бизнес-сервисов

Gateway отвечает за аутентификацию, а прикладные компоненты — за доступ и бизнес-политику. Для собственных операций `profile.user_id == identity.user_id` проверяется в Candidate DB: невозможно создать объект и тут же получить отказ только из-за задержки owner tuple. Для чужого доступа используется OpenFGA плюс актуальные lifecycle/visibility из БД. Владение не выводится из переданного candidate ID или file ID. Ошибка OpenFGA не включает fail-open.

Доверенный вызов File Service требует service identity и ограниченного grant/resource binding: общая service account не должна разрешать скачивание любого file ID. Политику доступа к файлам и привязкам нужно согласовать с File Service; прямые публичные S3 ACL не заменяют её. Сервис не пишет OpenFGA tuples синхронно в транзакции профиля — события обрабатывает общая AuthZ Synchronization Service. Для новых отношений применяется согласованный bootstrap/owner policy, а не распределённый SQL+OpenFGA commit.

### SQL и внешние операции

Изменение агрегата, его version, ключ идемпотентности, cleanup jobs и outbox выполняются одной локальной транзакцией. Сетевые запросы File Service не удерживают SQL-lock на время upload/сканирования. На границе используется operation ID, идемпотентные bindings, повторы и reconciliation, а не попытка включить S3 в PostgreSQL-транзакцию.

Идемпотентность привязана к actor + operation + key и хешу payload. Результат не отдаётся другому пользователю с тем же ключом. Ограничивается срок хранения ключей и согласуется поведение после expiry. Обычный optimistic update требует expected version; сервер возвращает конфликт, а не молча перезаписывает чужое изменение.

### Предлагаемые события

| События | Изменение | Минимальный payload |
|---|---|---|
| CandidateProfileCreated / Updated | Создание или профессиональные данные | candidate ID, owner user ID для AuthZ где необходим, version, changed fields без значений частных полей |
| CandidatePreferencesUpdated | Карьерные предпочтения | candidate ID, version; чувствительные ожидания не размножаются без отдельного контракта |
| CandidateJobSearchStatusChanged | Статус поиска | candidate ID, previous/new status, version |
| CandidateVisibilityChanged | Права публикации | candidate ID, visibility/contact policy, version |
| CandidateProfileArchived / Restored | Lifecycle профиля | candidate ID, lifecycle, version |
| ResumeVersionReady | Файл пригоден для использования | candidate ID, resume ID, version ID, file ID, version |
| ResumeMetadataUpdated / ActiveVersionChanged | Метаданные/выбор версии | candidate ID, resume ID, выбранный version ID где нужен, version |
| PrimaryResumeChanged | Основной документ | candidate ID, previous/new resume ID, selection version |
| ResumeDeleted | Удаление binding профиля | candidate ID, resume ID, version; технические cleanup jobs остаются в БД |

Единый envelope содержит event ID/type, aggregate ID/type/version, schema version и UTC occurredAt. Предлагаемый topic — `careeria.candidates.events.v1`, контракт Avro ещё требуется согласовать. События доставляются через существующий CDC/outbox-путь; Candidate Service не публикует их напрямую в Kafka. Потребители дедуплицируют event ID и обрабатывают версии, а не предполагают глобальный порядок между Profile и Resume. Байты резюме, тексты about, контакты, presigned URL и secrets в общем event payload отсутствуют.

### Снимок резюме при отклике

Hiring Service должен хранить выбранные resume ID + **неизменяемую version ID** и разрешённый snapshot профиля на момент Apply, а не «текущее основное резюме кандидата». Для файла требуется отдельный устойчивый File Service binding ресурса отклика. До подтверждения такого binding отклик нельзя считать сохранённым с гарантированно доступным документом; сбои разрешаются идемпотентностью/компенсацией, не общей транзакцией двух сервисов.

Изменение профиля, primary или activeVersion не переписывает ранее отправленные данные. DeleteResume освобождает binding профиля, не binding отклика. Доступ к историческому документу проверяет Hiring Service в контексте Application; Candidate GetResumeDownloadURL не открывает скрытый профиль через один заявленный application ID. Эта интеграция — требование к дальнейшему контракту Apply/File Service, а не молча добавленный прямой клиент Hiring на данной L3.

### Ошибки и наблюдаемость

Контракт различает Unauthenticated, недоступный ресурс, ValidationFailed, VersionConflict, InvalidState, AlreadyExists, FileNotReady, FileRejected, UploadExpired, DependencyUnavailable и RateLimited. Внешние ответы не раскрывают чужую ownership, точные причины антивирусного анализа или технический S3 key. Возврат gRPC-кодов и retry semantics нужно закрепить в protobuf/error model.

Нужны метрики upload-to-ready latency, stuck pending, размер/возраст cleanup backlog, retry/failed jobs, конфликты версий и отказы доступа; трассы по request/operation ID. Аудит записывает actor/resource/action/result без содержимого резюме, контактов, upload/download URL. Конкурентные переходы Cancel/Complete/Delete, сбой после File Service commit и restart worker покрываются отдельными интеграционными тестами.

## Что не включено автоматически

| Вопрос | Решение первой версии / следующий контракт |
|---|---|
| Удаление аккаунта и всех персональных данных | Archive не является удалением. Нужен отдельный межсервисный процесс с Identity, Hiring, Communication и File Service, подтверждением завершения и согласованным retention. Эта L3 не обещает удалить историю чужих сервисов. |
| Автопарсинг резюме / OCR / AI extraction | Не добавлены без требования. При появлении — асинхронный импорт с просмотром результата; файл не должен молча переписывать профиль. |
| Генерация PDF из структурированного профиля | Отдельный будущий сценарий; существующие resume files пока загружаются пользователем. |
| Аватар | Можно хранить file ID в профиле через тот же File Service, но upload/policy аватара — отдельный контракт, не resume endpoint. |
| Ссылки на профили и портфолио | Структурированные проверенные по форме URL; сервис не скрейпит сторонние сайты. |
| Полноценный поиск/рекомендации | Начальная SQL-выборка; отдельный индекс требует согласования L2 и событий, не добавлен «для красоты». |
| Retention версий и hiring snapshots | Нельзя удалять файл только потому, что он не activeVersion; File Service учитывает все bindings и согласованные сроки. |
| Параметры публикации и лимиты | Нужно утвердить поля минимального профиля, число документов/версий, типы/размер файлов, upload expiry, TTL ссылок и cleanup retry policy. |
| Состояние File Service | Begin/Confirm/Bind/Release/Reconcile — предложенные требования к его API. Согласовать протокол durable bindings и сборки orphan-файлов до реализации Candidate Service. |
