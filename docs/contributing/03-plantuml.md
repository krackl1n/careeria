# PlantUML и C4: исходники и страницы

PlantUML строит архитектурные диаграммы из `.puml`. В Careeria он используется прежде всего для C4: системного контекста, контейнеров, компонентов, тематических проекций и динамических сценариев. В отличие от IDEF0, PlantUML-схема встраивается непосредственно в Markdown-страницу как SVG при её сборке.

## Где находятся схемы

Исходники лежат в `docs/architecture/c4-plant-uml/plantuml/`. Выбирайте каталог по смыслу схемы:

| Каталог | Что описывает |
| --- | --- |
| `context/` | Системный контекст L1: пользователи, Careeria и внешние системы. |
| `container/` | Контейнеры L2: приложения, сервисы, БД и инфраструктура. |
| `component/` | Компоненты L3 внутри конкретного контейнера. |
| `projections/` | Срезы общей модели по теме или области команды. |
| `dynamic/` | Порядок взаимодействий в сценарии. |
| `model/` | Общие определения элементов и связей. |
| `common/` | Повторно используемые стили, теги и легенды. |

Обычно рядом с самостоятельным `.puml` есть `.md`-страница: она объясняет границы вида, основные элементы и переходы к соседним уровням. Исходник без страницы можно открыть как файл, но он не заменяет пояснение для читателя.

## Как подключить диаграмму

В Markdown-странице создайте блок с языком `plantuml`. Путь после `!include` считается от каталога `docs/`, потому что рендерер запускается из него:

````markdown
```plantuml
@startuml
!include architecture/c4-plant-uml/plantuml/context/system-context.puml
@enduml
```
````

Рабочий пример — [системный контекст](../architecture/c4-plant-uml/plantuml/context/system-context.md). Внутри самой схемы её собственные `!include` могут быть относительными к `.puml`-файлу. Пишите пояснение до и после блока: для чего нужен вид, что входит в его границу и куда идти за деталями.

Расширение `plantuml-markdown` из `mkdocs.yml` создаёт встроенный SVG. Это сохраняет кликабельные ссылки элементов; CSS в `docs/theme/diagrams.css` подстраивает ширину схемы под страницу.

| Настройка PlantUML в `mkdocs.yml` | Назначение |
| --- | --- |
| `plantuml_cmd: docs/tools/plantuml.sh pipe` | Запускает локальный рендерер из контейнера документации. |
| `format: svg_inline` | Вставляет SVG в HTML страницы, чтобы работали ссылки элементов. |

## Общие элементы и несколько представлений

Повторно используемые элементы и связи храните в `model/`, оформление — в `common/`. Схема подключает нужные фрагменты через `!include`, чтобы названия сервисов, связи и цвета не расходились между L1, L2 и L3.

Если в одном `.puml` нужны именованные части для отдельных страниц, ограничьте каждую часть `!startsub <ID>` и `!endsub`, а на странице подключите `!includesub <путь>!<ID>`. Это синтаксис [препроцессора PlantUML](https://plantuml.com/preprocessing). Пример подключения секции:

````markdown
```plantuml
@startuml
!includesub architecture/c4-plant-uml/plantuml/example.puml!L2
@enduml
```
````

Путь `example.puml` здесь условный: создайте такой исходник перед использованием. Если вид живёт в отдельном `.puml`, используйте обычный `!include`, как в текущих страницах C4.

## Переходы между уровнями

Для перехода с элемента диаграммы на страницу другого уровня укажите `$link` в объявлении C4. Например, элемент Careeria в [исходнике системного контекста](../architecture/c4-plant-uml/plantuml/context/system-context.puml) ведёт на `/architecture/c4-plant-uml/plantuml/container/full-system/`. Ссылка на `.md` в тексте страницы ведёт к той же цели без необходимости нажимать на SVG.

Адрес `$link`, начинающийся с `/`, рассчитан на размещение сайта в корне домена. При публикации в подкаталоге проверьте эти ссылки и адаптируйте их к базовому пути.

## Как синхронизируются изменения

При сборке страницы MkDocs рендерит её PlantUML-блоки через локальный `docs/tools/plantuml.sh`; публичный PlantUML-сервер не требуется. `make docs` обновляет страницу при изменении её Markdown. Если изменился общий `.puml`-фрагмент, `docs/tools/watch_plantuml_includes.py` находит зависимые страницы и помечает их для пересборки. Результат поэтому появляется в браузере после сохранения источника.

```sh
make docs                   # Просмотр страниц
make architecture-validate # Проверка исходников PlantUML
make docs-test              # Сборка, SVG и внутренние ссылки
```

После редактирования проверьте саму картинку: расположение блоков, подписи, пропорции и переходы. `make architecture-validate` проверяет исходники, а `make docs-test` — собранные страницы. Сгенерированные файлы в `.site-docs/` не редактируйте.
