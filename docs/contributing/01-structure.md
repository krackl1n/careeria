# Структура документации и новые страницы

Документация лежит в `docs/`. MkDocs строит из неё сайт: Markdown становится страницами, изображения и исходники диаграмм копируются как файлы. [Главная страница](../index.md) ведёт к содержательным разделам, а [руководство для авторов](index.md) — к правилам их редактирования.

## Каталоги и их назначение

| Путь в `docs/` | Что туда добавлять |
| --- | --- |
| `getting-started/` | Первый запуск документации и проекта. |
| `contributing/` | Правила структуры, Markdown и инструментов для диаграмм. |
| `project/` | Цели, роли, процессы, требования и проектные решения. |
| `architecture/` | Архитектурные представления, C4 и исходники PlantUML. |
| `idef0-svg/models/` | Исходные IDEF0-модели, настройки видов и полученные SVG. |
| `deployment/` | Развёртывание и окружения. |
| `security/` | Доступ, безопасность и проверки. |
| `theme/` | Стили сайта, включая размеры диаграмм. |
| `tools/` | Сборочные скрипты и проверки; это не страницы для читателя. |

Если тема разрастается, создайте подкаталог с `index.md` и дочерними `.md`-страницами. Например, `contributing/idef0/` содержит обзор, справочник команд и примеры; `contributing/plantuml-guide/` содержит обзор и справочник команд. В меню это вложенные разделы внутри «Как писать документацию». Порядок подразделов задают числовые префиксы файлов; заголовок H1 задаёт понятное имя пункта меню.

## Основные настройки сайта

Конфигурация находится в `mkdocs.yml`. Значения, важные при добавлении страниц:

| Поле | Что означает | Когда менять |
| --- | --- | --- |
| `site_name`, `site_description` | Название и описание всего сайта. | При изменении общего названия документации. |
| `docs_dir` | Каталог исходников; сейчас `docs`. | Обычно не менять: от него зависят ссылки и скрипты. |
| `site_dir` | Каталог результата; сейчас `.site-docs`. | Только при изменении способа публикации. |
| `theme` | Внешний вид и возможности меню темы Material. | При изменении общего интерфейса сайта. |
| `plugins` | Поиск по страницам. | При добавлении возможностей сборки сайта. |
| `markdown_extensions` | Таблицы, примечания, якоря и рендер PlantUML. | Когда нужен новый синтаксис Markdown для всех страниц. |
| `hooks` | Скрипты навигации и генерации IDEF0 перед сборкой. | При изменении процесса сборки, а не отдельной страницы. |
| `extra_css` | Общие CSS-файлы, в том числе для диаграмм. | При изменении общего оформления. |
| `extra.navigation.order` | Порядок верхних разделов меню. | Если раздел должен стоять выше или ниже соседних. |
| `extra.navigation.titles` | Подписи разделов меню. | Когда имя каталога не подходит читателю. |
| `exclude_docs` | Каталоги исходного инструментария и временных файлов, не включаемые в сайт. | Если добавился новый служебный каталог. |

Для обычной новой страницы править `mkdocs.yml` не требуется: достаточно создать `.md` в нужном разделе.

## Из чего состоит страница {#page-structure}

| Элемент | Правило | Зачем нужен |
| --- | --- | --- |
| `# Заголовок` | Один H1 в начале файла. | Имя страницы в меню и поиске. |
| `## Раздел` | Крупная тема внутри страницы. | Даёт читателю быстрый переход по содержанию. |
| `### Подраздел` | Деталь раздела; не пропускайте уровень заголовка. | Сохраняет понятную вложенность. |
| Вступление | Назовите предмет, границу описания и ожидаемый результат. | Помогает понять, относится ли страница к задаче читателя. |
| Схема или пример | Поместите рядом с пояснением; дайте подпись через текст и `alt`. | Изображение остаётся осмысленным вне контекста страницы. |
| Ссылки | Дайте переход к родительскому разделу, соседним страницам и исходнику схемы. | Упрощает проверку и дальнейшее редактирование. |

Для проектных решений прямо указывайте, описывается **целевая модель** или уже работающая реализация. Не называйте сервис реализованным только потому, что он есть на архитектурной схеме. Пишите короткими абзацами: одно утверждение или решение — один абзац, проверяемые перечни — списком или таблицей.

Шаблон новой страницы:

```markdown
# Название темы

Коротко: что описано, для кого и в каких границах.

## Задача и контекст

Что происходит сейчас или какое решение требуется.

## Модель или решение

Описание блоков, связей и ограничений. Если есть диаграмма, поместите её здесь.

## Проверка и связанные страницы

Как проверить утверждения и куда перейти за деталями.
```

## Ссылки и вложения

Путь в Markdown считается **от текущего `.md`-файла**. Например, с этой страницы ссылка на [системный контекст](../architecture/c4-plant-uml/plantuml/context/system-context.md) начинается с `../architecture/`. Для перехода к странице схемы используйте `.md`; ссылка на `.puml` или `.idef0` открывает исходник, а `.svg` — готовое изображение.

MkDocs преобразует ссылки на `.md` в адреса страниц сайта. После переноса страницы исправьте все относительные ссылки на неё и из неё. Фотографии и небольшие файлы кладите рядом со страницей или в её `assets/`; для картинки добавляйте осмысленное описание:

```markdown
![Декомпозиция процесса найма](../idef0-svg/models/hiring.svg)
```

Для диаграмм следуйте отдельным руководствам: [IDEF0](idef0/index.md), [пошаговые примеры IDEF0](idef0/03-practical-examples.md) или [PlantUML](plantuml-guide/index.md). Синтаксис каждой команды приведён в [справочнике IDEF0](idef0/01-commands.md) и [справочнике PlantUML](plantuml-guide/01-commands.md).

## Навигация и проверка

Новая `.md`-страница появляется в меню автоматически. `index.md` служит входом в раздел; верхние разделы упорядочены в `mkdocs.yml` через `extra.navigation.order`. В настройке `extra.navigation.titles` можно переименовать заголовок раздела, но обычно достаточно ясного H1 у `index.md`.

Перед завершением работы откройте страницу через `make docs`, проверьте меню, переносы строк на диаграммах и ссылки. Затем запустите `make docs-test`: он собирает сайт в строгом режиме, проверяет отрисовку PlantUML, актуальность IDEF0-SVG и локальные ссылки. Созданный `.site-docs/` не редактируйте и не добавляйте в Git.
