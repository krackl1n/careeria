# Команды IDEF0: полный справочник

Исходник диаграммы можно написать в блоке `idef0` на Markdown-странице или в отдельном файле `.idef0`. В обоих случаях функции и стрелки задаются одинаковыми строками. Команды с `@` работают **только внутри блока `idef0`**: они выбирают виды, цвета, туннели и экспорт. Для отдельного файла эти параметры задаются в соседнем `.idef0.json`.

````markdown
```idef0
@view focus `Обработать заявку`
`Обработать заявку` receives `Заявка`
`Обработать заявку` produces `Решение`
```
````

В Markdown-странице используйте внутренний блок из примера; внешняя рамка нужна только для его показа в этом справочнике. Готовый пример для копирования есть на [главной странице IDEF0](index.md#idef0-inline).

## Строки модели

Каждая строка имеет форму `` `Имя функции` receives `Имя стрелки` `` или `` `Родитель` is composed of `Дочерняя функция` ``. Команды и предикаты пишутся по-английски. Имена можно писать по-русски; отделяйте их бэктиками или парными кавычками `"..."`. Для одного и того же блока или потока повторяйте имя **точно**, включая регистр и пробелы: совпадение имён связывает стрелки между блоками.

| Предикат | Пример | Результат |
| --- | --- | --- |
| `receives` | `` `Проверить заявку` receives `Заявка` `` | Вход Input слева: данные, которые функция обрабатывает. |
| `respects` | `` `Проверить заявку` respects `Правила отбора` `` | Управление Control сверху: правило или ограничение. |
| `produces` | `` `Проверить заявку` produces `Результат проверки` `` | Выход Output справа: результат функции. |
| `requires` | `` `Проверить заявку` requires `Команда подбора` `` | Механизм Mechanism снизу: исполнитель или инструмент. |
| `is composed of` | `` `Обработать заявку` is composed of `Проверить заявку` `` | Дочерний блок на следующем уровне; это связь функций, а не стрелка. |

Для каждого дочернего блока добавьте отдельную строку `is composed of`. Так можно построить несколько уровней: `` `A` is composed of `B` ``, затем `` `B` is composed of `C` ``. Чтобы показать уровень B, добавьте `` @view decompose `B` ``. У модели должен быть один осмысленный корень; не задавайте циклы и не используйте одно имя для разных функций. Пустые строки и строки, начинающиеся с `#`, можно использовать для разделения и комментариев.

## `@view`: какой уровень показать

Форма: `` @view mode `Имя функции` ``. Имя можно опустить, чтобы выбрать корень модели. Добавьте несколько строк `@view`, если на странице нужны несколько схем из одного исходника; порядок строк определяет порядок схем и файлов `@export`.

| Режим | Что выводится | Пример |
| --- | --- | --- |
| `auto` | `decompose`, если у функции есть дочерние блоки, иначе `focus`. | `` @view auto `Обработать заявку` `` |
| `focus` | Один выбранный блок с его входами, правилами, выходами и механизмами. | `` @view focus `Обработать заявку` `` |
| `decompose` | Непосредственные дочерние блоки выбранной функции и их связи. Выбранная функция становится границей схемы. | `` @view decompose `Обработать заявку` `` |
| `schematic` | Конечные функции выбранной ветки на одной обзорной схеме. | `` @view schematic `Обработать заявку` `` |

Если `@view` нет, встроенный блок использует `auto` для корня. Имя после режима должно точно совпадать с именем функции в модели. Для функции без дочерних блоков используйте `focus` или `auto`.

## `@export`: отдельный SVG

Форма: `@export file-name.svg`. Команда необязательна; она сохраняет SVG рядом с Markdown-страницей, чтобы его можно было открыть, скачать или вставить на другую страницу. В одном блоке допускается один `@export`. Имя содержит только строчные латинские буквы, цифры и дефисы и заканчивается `.svg`.

```text
@export obrabotka-zayavki.svg
@view focus `Обработать заявку`
@view decompose `Обработать заявку`
```

Пример создаст `obrabotka-zayavki.svg` и `obrabotka-zayavki-2.svg` рядом с исходной страницей. Первый файл соответствует первой строке `@view`. Без `@view` создаётся один SVG. Сборка `make docs` и `make docs-build` обновляет файлы автоматически; `make idef0-render` делает это без сборки сайта. Если удалить `@export` или вид, ранее созданные SVG нужно удалить вручную.

## `@order`: порядок расположения блоков

Форма: `@order auto|source|fixed|heuristic`. Команда задаёт способ упорядочивания дочерних блоков по диагонали (слева сверху вниз направо).

| Режим | Поведение |
| --- | --- |
| `auto` (по умолчанию) | Автоматически сохраняет порядок объявления (`is composed of`), если он образует прямой поток или не уступает эвристике по числу обратных связей. |
| `source` / `fixed` | Строго фиксирует блоки в том порядке, в котором они объявлены через `is composed of` в исходнике модели. |
| `heuristic` | Включает алгоритм подбора позиций по минимальному числу обратных стрелок (может переставлять блоки местами). |

```text
@order source
```

## `@branching`: разветвление стрелок (Forking / Branching)

Форма: `@branching auto|mechanisms|none`. По стандарту IDEF0, если один и тот же внешний механизм (снизу) или управление (сверху) относится сразу к нескольким блокам, стрелка рисуется разветвлённой: общий вертикальный ствол от границы с одной подписью и ICOM-кодом, горизонтальная распределительная шина и стрелки-ответвления к целевым блокам.

| Режим | Поведение |
| --- | --- |
| `auto` (по умолчанию) | Автоматически объединяет дублирующиеся стрелки механизмов снизу и управлений сверху в разветвлённую линию. |
| `mechanisms` | Разветвляет только механизмы снизу. |
| `none` / `false` | Отключает разветвление и рисует отдельные параллельные стрелки для каждого блока. |

```text
@branching auto
```

## `@corners` и `@radius`: скругление поворотов стрелок

Форма: `@corners rounded [радиус]|sharp` или `@radius <число>`. Позволяет переключать вид изгибов стрелок и настраивать их радиус (по умолчанию радиус равен 8px). Функциональные блоки всегда остаются строгими прямоугольниками по стандарту IDEF0.

| Режим | Поведение |
| --- | --- |
| `rounded` (по умолчанию) | Сглаженные повороты стрелок (дуги Безье на изгибах). По умолчанию радиус 8px. Можно указать `@corners rounded 6` или `@radius 8`. |
| `sharp` | Строгие прямоугольные повороты под 90° без скруглений. |

```text
@corners rounded 8
# или отдельно:
@radius 8
```

## `@icom`: отображение ICOM-кодов стрелок

Форма: `@icom on|off`. Позволяет включать или отключать отображение буквенных кодов стрелок (`I1`, `C1`, `O1`, `M1` и т.д.) у границ диаграммы. Коды выравниваются плотно рядом со стрелкой и не «летают».

| Режим | Поведение |
| --- | --- |
| `on` (по умолчанию) | ICOM-буквы стрелок отображаются у границ диаграммы. |
| `off` | ICOM-буквы скрыты (в коде SVG сохраняются атрибуты `data-idef0-icom`). |

```text
@icom off
```

## `@callouts`: выносные пунктирные линии при смещении текста

Форма: `@callouts on|off`. При плотном расположении входящих стрелок (например, нескольких механизмов) их текстовые подписи автоматически разводятся по вертикальным уровням, чтобы предотвратить наложение текста. Если подпись смещена, от неё к стволу стрелки строится пунктирная выносная линия.

| Режим | Поведение |
| --- | --- |
| `on` (по умолчанию) | Отображает пунктирную выносную линию от стрелки к смещённой подписи. |
| `off` | Подписи по-прежнему не накладываются друг на друга, но пунктирная линия не рисуется. |

```text
@callouts on
```

## `@crossings`: обход пересечений стрелок

Форма: `@crossings arc|gap|none`. Задаёт вид отображения при пересечении линий (например, при наличии обратных связей).

| Режим | Поведение |
| --- | --- |
| `arc` / `bridge` (по умолчанию) | Мостик-полукруг (дуга радиусом 5px), перепрыгивающий пересекаемую линию. Классический вид инженерных схем. |
| `gap` / `break` | Микро-разрыв (пробел) в линии в точке пересечения. |
| `none` / `plain` | Без обхода: сквозное пересечение линий крест-накрест. |

```text
@crossings arc
```

## `@defaults`: общие цвета

Форма: `@defaults ключ=цвет [ключ=цвет ...]`. Можно указать один или несколько ключей; значения действуют на всю диаграмму. Допустимы `#RGB`, `#RRGGBB` и буквенное имя CSS-цвета, например `red`. Формы `rgb(...)` и прозрачность здесь не поддерживаются.

| Ключ | Что окрашивает |
| --- | --- |
| `arrow` | Линии и наконечники всех стрелок. |
| `arrow_text` | Подписи всех стрелок. |
| `block_fill` | Фон всех блоков. |
| `block_stroke` | Контуры всех блоков. |
| `block_text` | Названия функций внутри блоков. |

```text
@defaults arrow=#43566D arrow_text=#26384B block_fill=#F3F7FB block_stroke=#27466A block_text=#172B41
```

Без настройки фон блока остаётся прозрачным, линии и текст — чёрными. Индивидуальные настройки ниже имеют приоритет над `@defaults`.

## `@block`: цвет конкретного блока

Форма: `` @block `Точное имя функции` | ключ=цвет [ключ=цвет ...] ``. Имя совпадает со строками модели. Команду можно повторить для разных блоков.

| Ключ | Что окрашивает |
| --- | --- |
| `fill` | Фон блока. |
| `stroke` | Контур блока. |
| `text` | Название функции. |

```text
@block `Подготовить решение` | fill=#EAF6EE stroke=#15803D text=#14532D
```

## `@arrow`: цвет стрелки

Форма: `` @arrow `Точное имя стрелки` | ключ=цвет [ключ=цвет ...] ``. Если имя встречается на нескольких уровнях, цвет применяется ко всем стрелкам с этим именем.

| Ключ | Что окрашивает |
| --- | --- |
| `stroke` | Линию и наконечник стрелки. |
| `text` | Её подпись. |

```text
@arrow `Решение по кандидату` | stroke=#15803D text=#14532D
```

## `@tunnel`: явное различие границ

Форма: `` @tunnel parent|child | `Раскрываемая функция` | input|control|output|mechanism | `Точное имя стрелки` ``. Команда требуется, когда интерфейс родительского блока отличается от внешней границы его дочерней диаграммы. Проверка сравнивает одновременно роль и имя стрелки.

| Сторона | Когда писать | Что увидит читатель |
| --- | --- | --- |
| `parent` | Стрелка есть на родительском блоке, но опущена на дочерней диаграмме. | Скобки у стрелки родительского блока. |
| `child` | Стрелки нет на родительском блоке, но она входит в дочернюю диаграмму или выходит из неё. | Скобки на границе дочерней схемы; ICOM-код этой стрелке не присваивается. |

```text
@tunnel parent | `Проверить отклики` | control | `Политика найма`
@tunnel child | `Проверить отклики` | mechanism | `Инструмент отбора`
```

Обычные граничные стрелки автоматически получают код `I1`, `C1`, `O1` или `M1` по интерфейсу родительского блока. Внутренние стрелки между дочерними блоками не объявляют туннелями. Команда `@tunnel` должна описывать **ровно фактическое** различие: лишний, пропущенный или неверно названный туннель вызывает ошибку `boundary mismatch`. Для корневой функции `parent` использовать нельзя.

## Параметры отдельной модели `.idef0.json`

Файл `<имя>.idef0.json` лежит рядом с `<имя>.idef0` в `docs/idef0-svg/models/`. Он нужен для нескольких видов, цветов и туннелей у отдельно хранимой модели. Сами строки модели остаются в `.idef0`.

| Ключ | Эквивалент в блоке `idef0` | Значение |
| --- | --- | --- |
| `mode` | `@view` для основного SVG | Режим основного `<имя>.svg`; по умолчанию `decompose`. |
| `process` | Имя после `@view` | Функция основного SVG; по умолчанию корень. |
| `views` | Дополнительные `@view` | Массив объектов дополнительных видов. |
| `views[].name` | Суффикс файла после `@export` | Уникальный суффикс из строчных латинских букв, цифр и дефисов. |
| `views[].mode` | Режим дополнительного `@view` | `focus`, `decompose` или `schematic`. |
| `views[].process` | Имя после дополнительного `@view` | Точное имя функции. |
| `defaults` | `@defaults` | Объект с ключами `arrow`, `arrow_text`, `block_fill`, `block_stroke`, `block_text`. |
| `blocks` | `@block` | Объект по именам функций; у каждой `fill`, `stroke`, `text`. |
| `arrows` | `@arrow` | Объект по именам стрелок; у каждой `stroke`, `text`. |
| `boundaries.<функция>.parent_tunnels` | `@tunnel parent` | Объект с ролями и массивами имён стрелок, опущенных на дочерней схеме. |
| `boundaries.<функция>.child_tunnels` | `@tunnel child` | Объект с ролями и массивами имён стрелок только на дочерней схеме. |
| `order` | `@order` | Способ упорядочивания блоков: `auto`, `source`, `fixed`, `heuristic`. |
| `branching` | `@branching` | Режим разветвления стрелок: `auto`, `mechanisms`, `none`. |
| `corners` | `@corners` | Скругление поворотов стрелок: `rounded`, `sharp`. |
| `crossings` | `@crossings` | Обход пересечений: `arc` (мостик), `gap` (разрыв), `none` (сквозное). |

Для `views[].mode` и основного `mode` генератор отдельных файлов принимает `focus`, `decompose`, `schematic`; `auto` доступен в `@view` встроенного блока. [Полный пример JSON](../../idef0-svg/models/hiring.idef0.json) показывает все группы настроек.

## Команды сборки

Запускайте их из корня репозитория. Нужен Docker Compose.

| Команда | Что делает |
| --- | --- |
| `make docs` | Запускает сайт с обновлением страниц и SVG после сохранения исходников. |
| `make idef0-render` | Обновляет SVG отдельных моделей и блоков с `@export` без сборки сайта. |
| `make docs-build` | Собирает статический сайт в `.site-docs/` со строгой проверкой MkDocs. |
| `make docs-test` | Проверяет генерацию IDEF0, собирает сайт и проверяет локальные ссылки. |

Если сборка пишет `boundary mismatch`, сначала сравните стрелки родительского блока и внешнюю границу его декомпозиции по роли и имени. Затем исправьте модель или объявите ровно нужные `@tunnel` либо `boundaries`. Готовый код с пошаговым разбором есть в [примерах с русскими названиями](03-practical-examples.md), а работа с отдельными файлами показана в [примерах IDEF0](02-examples.md).

## Как показываются ошибки {#idef0-errors}

При `make docs` неверный блок `idef0` заменяется заметной панелью «Ошибка IDEF0» прямо на той странице, где он написан. В панели указан путь к Markdown-файлу, строка и сообщение генератора. Остальные корректные схемы на странице продолжают отображаться. Например, для неверного режима:

```text
docs/project/otkliki.md:8: IDEF0: use @view auto|focus|decompose|schematic [Process Name]
```

Если ошибочен отдельный `.idef0` или `.idef0.json`, изображение на странице заменяется панелью ошибки; сообщение также появляется вверху страниц сайта и в логах контейнера. На месте сгенерированного SVG записывается изображение с текстом ошибки, поэтому прямая ссылка на SVG тоже показывает ошибку. Ошибка в блоке с `@export` также заменяет встроенную диаграмму и изображения, подключённые к созданному SVG.

После исправления сохраните файл: панель исчезнет при следующей пересборке. Ошибки IDEF0 записываются в лог, а сборка документации и `make idef0-render` продолжаются. Другие проверки `make docs-test`, например проверка ссылок, по-прежнему могут завершиться с ошибкой.
