# Конкурентные изменения данных

Для проектируемых сервисов основной способ изменения агрегата — оптимистичная проверка версии. Сервис читает состояние и `version`, применяет доменные правила и в короткой транзакции выполняет условное обновление корня с ожидаемой версией. При успехе версия увеличивается; связанные записи и outbox фиксируются в той же транзакции. Например:

```sql
UPDATE vacancies
SET title = $1, version = version + 1, updated_at = $2
WHERE id = $3 AND version = $4
RETURNING version;
```

Ноль возвращённых строк не означает успех: запись могла измениться, исчезнуть или стать недоступной. Сервис повторно определяет допустимый ответ без раскрытия чужого ресурса; при конфликте клиент получает согласованную ошибку и может перечитать данные. Нельзя автоматически повторить команду с новой версией, не повторив авторизацию и доменные проверки. Для фоновых безопасных операций допустим ограниченный повтор всей транзакции после повторного чтения. Точная форма ошибки и правила retry определяются API.

Для агрегата в нескольких таблицах версия принадлежит корню: успешный CAS и изменение дочерних строк выполняются на одном соединении в одной транзакции. Если CAS не прошёл или запись дочерних строк/outbox завершилась ошибкой, вся транзакция откатывается. CAS защищает только данные, изменения которых обязаны увеличивать проверяемую версию. Он не устраняет автоматически write skew, гонку с отзывом членства или межсервисную несогласованность.

## Общие инварианты

Если правило затрагивает несколько агрегатов, нужен единый протокол конкуренции. Предпочтителен общий versioned guard: **все** конкурирующие команды атомарно проверяют и увеличивают версию одной управляющей записи, а затем в той же транзакции повторно проверяют правило и меняют зависимые строки. Например, изменение участника и архивация профиля могут использовать версию профиля; отправка сообщения и изменение состава — версию диалога. Сам SQL `UPDATE` при этом берёт необходимые кратковременные блокировки строки: «оптимистичный» означает отсутствие долгой блокировки при чтении и проверку ожидаемой версии, а не отсутствие блокировок в PostgreSQL.

Если гарантировать участие всех путей в протоколе невозможно или нужно захватить ограниченный набор задач, применяется короткая явная блокировка в фиксированном порядке, уникальный индекс или `SERIALIZABLE` с обработкой конфликтов. Например, защиту последнего владельца нельзя обеспечить только независимыми версиями двух разных Member: одновременные изменения могут оставить ноль владельцев. Аналогично один optimistic version не делает атомарными PostgreSQL и File Service. Версионная проверка и ограничения БД дополняют друг друга.

## Очереди и внешние операции

Для claim фоновых задач сохраняется `FOR UPDATE SKIP LOCKED` в короткой транзакции с записью lease/token; CAS и token проверяются при завершении. `SKIP LOCKED` без lease после commit недостаточен, а fencing token не отменяет уже начатый сетевой вызов. Выдача URL, S3, Runner, LiveKit и HTTP выполняются вне блокировок SQL; при возврате используется CAS по актуальной версии и повторная проверка состояния. Временные дедлайны и полномочия проверяются заново в момент условного перехода согласно контракту.

В системах с высокой конкуренцией общий guard может стать горячей строкой, а массовые retries — увеличить нагрузку. Выбирать общий guard, явную блокировку или другое разбиение следует по инварианту и измерениям. Нужны интеграционные тесты PostgreSQL на параллельные транзакции, откат дочерних записей и outbox, проверку прав, пропущенный CAS и дедлайны. PGlite-проверка синтаксиса таких гарантий не доказывает.

Identity уже частично реализован и не меняется этой проектной политикой: для него требуется отдельно проверить код, транзакции и миграции, прежде чем утверждать наличие ожидаемой версии на каждом агрегате или менять рабочие таблицы.
